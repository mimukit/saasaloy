# Plan: the `env` capability

Grilled: 2026-09-20

Issue: [#153](https://github.com/mimukit/saasaloy/issues/153). Companion: [#154](https://github.com/mimukit/saasaloy/issues/154) (`config`). Touches [#152](https://github.com/mimukit/saasaloy/issues/152) (`db:setup`), which must write `.env`.

## Context

A scaffolded saasaloy project has no owner for its environment values. Each capability factory takes `env` in whole and reads whichever key it needs, so a missing key surfaces as a throw from inside `createEmail`, `createKv` or Better Auth, on the first request that needs it. The CLI knows more than the runtime does: `envVars` in each module descriptor carries the key and a human description, `saasaloy add` renders `apps/api/.dev.vars.example` from it, and `saasaloy env` prompts for values and writes them. None of that reaches the Worker.

Four problems sit on top of that.

**Every value lives in a per-workspace file.** `apps/api/.dev.vars`, `apps/web/.env`, `apps/admin/.env`. A key two apps read is written twice and drifts once.

**`.dev.vars` is a wrangler-only name.** Wrangler 4.131 reads `.env` when no `.dev.vars` sits beside it, and so does `@cloudflare/vite-plugin` 1.54.4. Vite and Astro read `.env` too. One name serves all three runtimes, and a leftover `.dev.vars` hides `.env` from wrangler, which is a silent failure.

**Which app reads a key is guessed.** `packages/cli/src/lib/env-vars.ts` infers the target workspace from the manifest, the `PUBLIC_` prefix and the wrangler config, and reports `ambiguous` when it cannot decide. The comment in that file says it plainly: `envVars` is a flat map with no app scope.

**Nothing stops a secret reaching a public bundle.** `modules/admin/files/vite.config.ts` sets `envPrefix: "PUBLIC_"`, and `modules/waitlist/files/web/components/WaitlistForm.tsx` reads `import.meta.env.PUBLIC_API_URL ?? "http://localhost:4000"`. The prefix is a convention nothing enforces, the fallback is silent, and `modules/waitlist/files/web/types/waitlist-env.d.ts` hand-augments `ImportMetaEnv` to make one key typecheck.

`~/projects/unishopr-reborn/packages/env` solves the distribution half in production. [t3-env](https://github.com/t3-oss/t3-env) solves the typing and leakage half. This plan takes the file layout and the pull from the first, the schema composition and the server/client split from the second, generates the key list from the descriptors the CLI already reads, and puts Infisical behind a provider contract.

Success: a scaffolded project has one tracked key list, one command that writes every service's `.env`, a typed `createEnv` per workspace that fails naming every missing key at once, a public bundle that cannot compile a server key into itself, no `.dev.vars` anywhere, and an optional `saasaloy add env-infisical` that pulls the values from a secrets service.

## Design decisions (settled)

| Decision | Resolution |
|----------|-----------|
| What the capability owns | One `packages/env` workspace with both halves. Node side: the key list, the distribution command, `env-exec`. Runtime side: `createEnv`, which validates and returns typed values. |
| Where it ships | The base template, not a module. The key list is the CLI's own output format, so `saasaloy init` writes it before any module is added and the CLI has one target instead of a fallback path. ADRs 0022 and 0027 made the same argument for the design layer. |
| File name | `.env` everywhere. No `.dev.vars`, no `.dev.vars.example`, no per-workspace example. |
| The key list | One tracked file, `packages/env/.env.example`, generated by `saasaloy add` from the installed modules' `envVars`. It replaces `apps/api/.dev.vars.example`. |
| What a service is | A workspace that reads a `.env` at runtime or build: `api`, `web`, `admin`, `infra`. The name is the workspace directory, not the module. |
| Who writes the service table | The base seeds the `web` row. `api`, `admin` and `infra` each append theirs with a `const-array` patch, which already has a removal inverse. `update` never rewrites the file, so ADR 0034 needs no exception. |
| How a key reaches a service | The descriptor declares it. A new top-level `envServices` field holds a `default` list plus per-key overrides. `envVars` keeps its `NAME → string` shape. |
| Fallback for a descriptor with no `envServices` | The `PUBLIC_` prefix rule alone, with a warning naming the module: a prefixed key goes to every client service, everything else to the api. `routeVariable` and its `ambiguous` prompt are deleted. |
| Where field definitions live | Each capability package exports an env preset, and each service's `createEnv` composes them with `extends`. No generated fields file, no `envTypes` in the descriptor. The schema sits in the file that already knows what the key means. |
| Drift between preset and descriptor | A repo test over `modules/*`, beside `scripts/table-names.test.ts`, plus a `saasaloy doctor` check in the scaffolded project. |
| Where `createEnv` is called | One `env.ts` per service workspace, each with an `extends: []` literal that capability modules patch. Two patch points is the honest cost of the server/client split, and `apps/web/src/env.ts` importing a server preset is then a visible mistake. |
| Validation trigger | On the first `createEnv(env)` call in an isolate, memoized per `env` object with a `WeakMap`. A Worker cannot see `env` at module scope, so first-request is the earliest honest point. |
| Server, client, shared | t3-env's full split. A `client` key that lacks `PUBLIC_` fails `typecheck`, and a Proxy throws when client code reads a server key. `isServer` is a build-time constant the CLI sets per workspace, because a Worker is a server and `typeof window === "undefined"` is true in both. |
| The frontend's keys | A hand-written strict map per app, t3-env's `runtimeEnvStrict`. Vite inlines a literal `import.meta.env.PUBLIC_X` and nothing else, so no derived or generated form can work. A module shipping into `apps/web` patches that map. |
| Validator | `zod` enters the base. `packages/env` types against Standard Schema, so the validator stays swappable, and ships zod as the default. The pin is declared once and `pnpm deps:verify` proves it. `validators` drops its own zod patch and keeps `@hono/zod-validator`. |
| Escape hatches | `emptyStringAsUndefined` defaulted to `true`, against t3-env's `false`, because `isSet` in `lib/env-vars.ts` already calls `KEY=` a placeholder. `skipValidation` reads a build-time flag, never a runtime key. `onValidationError` is overridable. |
| Value source | A provider contract inside `packages/env`. The built-in `local` source reads a gitignored `packages/env/.env`. `saasaloy add env-infisical` registers a second source through a `plugin-array` patch. |
| `saasaloy env` | Survives, prompting into the gitignored `packages/env/.env`, which is what the `local` source reads. Every gitignore guard in `commands/env.ts` keeps working. `--check` checks the distributed `.env` files. |
| Per-checkout values | `services.ts` carries a `CHECKOUT_OWNED_KEYS` list. A key named there survives a pull whoever wrote it, so `db:setup`'s branch `DATABASE_URL` is safe and `packages/env` never learns what a database is. |
| Production values | Each service row declares `dev` or `prod`, and `--env prod` refuses to act without `--only <service>`. Two independent guards on the one command that can put a live credential on disk. |
| Deploy path | Unchanged. `infra` uploads from `infra/.env`; a project without `infra` copies the printed `wrangler secret put` lines. `env-infisical` fills a file and is never in the upload path. |
| `process.env` | The rule binds runtime capability code, not node tooling. Nothing under a `packages/*/src` a Worker imports reads it. `scripts/env-setup.ts` reads `INFISICAL_CLIENT_ID` from it, and `infra` still calls `createEnv` on the object `env-exec` parsed. The ADR states the boundary. |
| `env` versus `config` (#154) | `env` owns per-deployment values the platform supplies at runtime, secret or not. `config` owns values checked into the repo and identical in every deployment. |
| Rollout | One issue, one long-lived branch. Each phase is its own commit, rebased onto `main` between phases to limit rot. |

## Approach

### What this reuses

- **`~/projects/unishopr-reborn/packages/env`** is the reference for `services.ts`, `dotenv.ts`, `env-file.ts`, `example.ts`, `check.ts`, `infisical.ts`, `pull.ts`, `exec.ts`, `setup.ts`. The section parser, the merge, the offline rule, the blank-on-purpose marker and `CHECKOUT_OWNED_KEYS` port nearly as-is.
- **t3-env** supplies the API shape: `extends` composition, `clientPrefix` enforcement, `runtimeEnvStrict`, `emptyStringAsUndefined`, `skipValidation`, `onValidationError`, `onInvalidAccess`, and Standard Schema as the validator interface. None of its code ships; it reads `process.env`, which this repo forbids, and validates at module scope, which a Worker cannot.
- **`packages/cli/src/lib/dev-vars.ts`** already renders an example file from descriptor `envVars` and merges it with what exists. Retarget it and teach it the section line.
- **`packages/cli/src/commands/env.ts`** already loads declarations from pinned descriptors, refuses to write into a file git does not ignore, and prints the production secret commands. Keep all of it; replace the routing and the target file.
- **`modules/kv/files/src/index.ts`**'s `defineKv({ providers: [] })` is the registry shape the value-source registry and every `extends: []` literal copy.
- **`scripts/table-names.test.ts`** is the shape of the drift test.
- **`modules/api/files/src/index.ts`**'s open `Bindings` interface stays assignable to the env types `createEnv` infers.

### Phase 1: `packages/env` in the base (built 2026-09-20)

Scaffold `packages/cli/templates/base/packages/env/`.

- `src/services.ts` — the service table. The base seeds the `web` row. Each row carries `file`, `folders`, `environment` and `omit`. `CHECKOUT_OWNED_KEYS` and `selectServices` live here.
- `src/dotenv.ts` — line-based parse, merge and format. Comments and ordering survive byte for byte.
- `src/env-file.ts` — read and write one file; delete a leftover `.dev.vars` after carrying its values across.
- `src/example.ts` — the `# @services` section parser and one service's slice of the example.
- `src/check.ts` — the blank-on-purpose marker and the completeness check.
- `src/sources.ts` — the value-source contract and `defineSources({ sources: [] })`, the `plugin-array` patch point. The built-in `local` source reads the gitignored `packages/env/.env`.
- `src/exec.ts` — the `env-exec` bin, so `infra`'s pulumi scripts need no `source`.
- `scripts/env-setup.ts` — `pnpm env:setup`, added to the root scripts by `package-json-script` patch.
- `.env.example` — seeded with a header and the base's own keys.
- `package.json` with a `clean` backed by exact-pinned `rimraf`, and `test` on `node --test`.

`.gitignore` needs no change: `_gitignore` already ignores `.env` and `.env.*` and unignores `*.env.example`.

Verification: `node --test` over the parse, the merge, the section rules, the completeness check, `CHECKOUT_OWNED_KEYS` and the `--env prod` guards, with no network and no write outside a temp directory.

### Phase 2: typed access (built 2026-09-20)

- `src/schema.ts` — the Standard Schema surface `packages/env` types against, and the re-exports a preset author uses. zod is the default and is declared in the base.
- `src/define.ts` — `createEnv({ extends, server, client, shared, clientPrefix, runtimeEnv | runtimeEnvStrict, isServer, emptyStringAsUndefined, skipValidation, onValidationError, onInvalidAccess })`.
- A `client` key without the `PUBLIC_` prefix is a type error. A server key read while `isServer` is false throws through the Proxy.
- Validation aggregates: one throw naming every failing key, its declaring module and the descriptor's own wording. A deploy with three unset keys takes one round trip to fix.
- `emptyStringAsUndefined` defaults to `true`. `skipValidation` reads a build-time constant only.
- No file under `src/` that a Worker imports reads `process.env`.

Verification: unit tests for each option, the aggregate message, the memoization, the prefix type error (a `tsd`-style negative test or an `@ts-expect-error` line), the Proxy throw, and a test proving the package declares no runtime dependency beyond the validator.

### Phase 3: presets and composition (built 2026-09-20)

- Each capability package gains `src/env.ts` exporting its preset. `packages/kv` declares `KV_PROVIDER` and `KV_KEY_PREFIX`; `packages/email` declares `EMAIL_PROVIDER` and `EMAIL_FROM`; and so on across nine capabilities.
- `apps/api/src/env.ts` and `apps/web/src/env.ts` each hold an `extends: []` literal. The `api` and `admin` modules ship theirs; the base ships `apps/web`'s.
- Every capability module gains a `plugin-array` patch appending its preset, beside the one that appends its provider.
- `apps/web/src/env.ts` and `apps/admin/src/env.ts` carry the hand-written `runtimeEnvStrict` map. `waitlist` patches `PUBLIC_API_URL` into it and its `waitlist-env.d.ts` is deleted.
- The `?? "http://localhost:4000"` fallbacks in `WaitlistForm.tsx` and `modules/admin/files/src/lib/auth.ts` go away; the key is required and the local default lives in the example.
- `scripts/env-presets.test.ts` fails when a preset declares a key the descriptor's `envVars` does not, or the reverse.

Verification: `pnpm lint`, the new drift test, and a `.dev` scaffold whose `apps/web` fails to build when `PUBLIC_API_URL` is unset.

### Phase 4: the descriptor declares services (built 2026-09-20)

- Add `envServices` to `packages/cli/schemas/registry-item.schema.json`: an optional object with a `default` array and per-key overrides, values drawn from the known service names.
- Migrate all 18 in-repo descriptors. About 40 keys.
- Teach `lib/dev-vars.ts` to render `packages/env/.env.example` with a `# @services` line per section, keys grouped by service set, each carrying its module's description and its `devVars` default.
- Delete `routeVariable`, its `ambiguous` branch and the workspace-inference helpers in `lib/env-vars.ts`. The `PUBLIC_` fallback replaces them in about three lines.
- Add the `saasaloy doctor` drift check.
- Add the rule to `.agents/skills/create-module/` and `create-provider/`.

Verification: `pnpm lint`, the CLI suite, and a `.dev` scaffold producing a correct example file with correct section lines.

### Phase 5: retire `.dev.vars` (built 2026-09-20)

- `saasaloy env` writes `packages/env/.env`, never `.dev.vars`. `--check` checks the distributed files.
- `saasaloy add` stops writing `apps/api/.dev.vars.example`.
- `saasaloy doctor` fails on an existing `.dev.vars`, naming the keys to move.
- `env:setup` carries a leftover `.dev.vars`'s values into `.env` and deletes it, so an existing project migrates by running one command.
- `#152`'s `db:setup` writes `DATABASE_URL` into `apps/api/.env`, protected by `CHECKOUT_OWNED_KEYS`.
- The base `_gitignore` drops its `.dev.vars` lines.

This is the breaking commit. It needs a `feat!` subject and a release note.

Verification: a scaffolded `.dev` project runs `pnpm dev` with values only in `.env`, and `saasaloy doctor` is clean. A project scaffolded before this plan migrates with one `pnpm env:setup`.

### Phase 6: `env-infisical` (built 2026-09-20)

- `modules/env-infisical/` following `.agents/skills/create-provider/`: one runtime file plus its registration patch into `packages/env`'s `sources` array.
- Machine identity through `INFISICAL_CLIENT_ID` and `INFISICAL_CLIENT_SECRET`, falling back to the host `infisical login`. Credentials travel in the child environment, never in argv, and no value is printed.
- The offline rule: when Infisical does not answer, keep the files that are complete and warn; fail and write nothing when one is missing or incomplete. An error Infisical did answer with, such as no access, always fails.
- Map its failures onto the capability's error codes and keep the raw one in `providerCode`.

Verification: a fake CLI on `PATH` answers for Infisical, so nothing opens a connection.

### Phase 7: the record (built 2026-09-20)

- ADR: `env` versus `config`, one rule.
- ADR: `.env` and not `.dev.vars`, naming the wrangler and vite loader versions.
- ADR: the `process.env` boundary — runtime capability code never, node tooling freely.
- The `saasaloy-env` skill: adding a key in two steps, the section rule, the server/client split, the offline rule.
- `CONTEXT.md` entries for *service*, *key list*, *value source*, *checkout-owned key*, *preset*.
- Update `AGENTS.md` and every module skill that names `.dev.vars.example`.

## Open questions

None blocking. Two to watch during the build.

- **The `isServer` build-time constant** has to be set per workspace by something. A `define` in `vite.config.ts` and `astro.config.mjs` is the obvious mechanism, and the Worker side may be able to assume `true` outright. Settle it in Phase 2 against a real build.
- **Standard Schema with zod in the base** makes the swap theoretically free, and no second validator will be exercised in this plan. The first project that swaps one in is the real test.

## Non-goals

- The `config` capability (#154). This plan settles the boundary rule and stops.
- A second secrets provider (Doppler, 1Password, AWS Secrets Manager). The contract must make one cheap; building one here does not prove that.
- Uploading secrets to a live account. `saasaloy env` prints `wrangler secret put` lines and does not run them.
- Runtime fetching of values from Infisical inside the Worker. Values arrive as bindings and secrets.
- Changing how `infra` uploads Worker secrets.
- A custom oxlint rule for env access. The type error and the Proxy cover it.
