# Plan: A docs site at /docs that stays true to the code

Grilled: 2026-11-19

## Context

Saasaloy's reader-facing docs live in `docs/wiki/`, 11 Markdown pages that the public site links to on GitHub (`DOCS` in `apps/web/src/content/landing.ts`). Most readers of these pages are AI agents that build a product with Saasaloy or change Saasaloy itself, so the docs are part of the product's agent surface, beside `llms.txt` and the bundled skills.

The pages drift. Every page ends with `_Verified against main@42cbf03 on 2026-09-11._`, and `main` has 827 commits after that one, of which 65 touched `docs/wiki/`. `docs/wiki/modules.md` lists 50 of the 56 modules: `ci`, `cms`, `e2e`, `ecommerce`, `env-infisical` and `file-uploads` are missing. The landing catalog shows all 56, because `apps/web/src/lib/module-registry.ts` reads every `registry-item.json` at build time. The hand-written table went stale and the generated one did not.

The owner wants a docs site at `/docs` beside the landing page, focused on AI-native and agentic development, with interactive parts that explain ideas and show how modules connect. The main concern is keeping it current with day-to-day changes.

Goal: a reader, human or agent, finds docs at `saasaloy.com/docs` that match the CLI version npm serves, and a change that makes a page wrong is caught in the pull request that makes it.

Target: 56 of 56 modules appear in the docs (baseline 50 of 56, from `docs/wiki/modules.md` against `ls modules/` on 2026-11-19). Every generated page matches its source, checked by `pnpm docs:check`. `pnpm docs:freshness` lists no hand-written page whose covered code changed after its stamp (baseline 11 of 11 pages, stamped at `42cbf03`). The owner accepted these targets in the grill on 2026-11-19.

## Design decisions (settled)

| Decision | Resolution |
|----------|-----------|
| Where the site lives | Inside `apps/web`, at `/docs`. One deploy, one design system, one set of gates. A second app was rejected: it doubles the deploy and the brand files. |
| Which version production describes | The released one. The owner releases a new CLI version from `main` by hand, and the same release publishes the site, built from the release commit (grill Q1, 2026-11-19). This replaces the first pick, "deploy from `main` with an unreleased marker on each page". |
| What runs the deploy | A release-it `after:release` hook in `packages/cli/.release-it.js`, on the owner's machine. It builds `apps/web` and runs `wrangler deploy --tag v<version> --message "saasaloy v<version>"`, so the Cloudflare Worker version carries the release tag (grill Q15, asked). The owner accepts that the site can go live before the npm publish job of plan 0112 finishes. A job in `publish.yml` and a hand step in a checklist were rejected. |
| A deploy hook that fails | The tag and the GitHub Release already exist, and release-it cannot undo them. The hook prints the rerun command, `git checkout v<version> && pnpm --filter @saasaloy/web deploy:production`, and exits non-zero (grill Q19, defaulted). |
| A dry run | `pnpm release:dry` shows the hook and does not deploy (grill Q20, defaulted). Phase 6 checks this, because release-it's dry-run handling of hooks is not yet confirmed in this repo. |
| A site-only fix between releases | It ships with a patch release, for example `v0.9.1`. No side door deploys `main` to production (grill Q14, asked). |
| The version on the page | Each docs page header shows the CLI version from `packages/cli/package.json`, for example "saasaloy v0.9.0". A build whose `HEAD` is not a `v*` tag (dev, a PR build) shows one banner, "Built from `main`, N commits after v0.9.0". There is no per-page "unreleased" marker, because production is always built at a tag (grill Q16, defaulted). |
| Order with plan 0112 | Phase 6 edits `packages/cli/.release-it.js`, which plan 0112 (#358) also changed. The grill made Phase 6 wait for #358 (grill Q17, defaulted). PR #360 merged #358 on 2026-11-19, so no phase waits now. Phase 6 adds its hook beside `before:init` in the merged file, where release-it no longer publishes to npm. |
| Layout | A custom layout in `apps/web` that follows `apps/web/DESIGN.md` and `brand.css`, not Starlight. Settled by the owner on 2026-11-19. Starlight would bring its own CSS, sidebar and type scale, which the blueprint style then has to fight. |
| Source of the prose | `docs/wiki/` stays the one source. An Astro content collection reads it in place with the `glob` loader. Nothing is copied into `apps/web`. |
| Markdown dialect in the wiki | Plain `.md` that reads correctly on GitHub and in an agent's context. No MDX in `docs/wiki/`. Settled by the owner on 2026-11-19. |
| Interactive blocks in a wiki page | A fenced code block with a reserved language, for example `saasaloy-graph`. GitHub shows it as a code block. A remark plugin in `apps/web` replaces it with a React island. An unknown `saasaloy-*` language fails the build. |
| Interactive-only pages | Under `apps/web/src/pages/docs/`. The codebase tour is one, in its own plan. |
| Front matter in wiki pages | None. GitHub renders front matter as a table. Page facts stay in the existing `docs/wiki/.wikimap.yaml`, which already holds a `documents:` glob list for each page. The sidebar order and titles come from that file, with a new `title:` and `section:` per entry. |
| Links between pages | A remark plugin rewrites a relative link. A link to another wiki page becomes a `/docs/...` URL. A link to any other repo file (`../adr/...`, `../../CONTEXT.md`) becomes a `github.com/mimukit/saasaloy/blob/v<version>/...` URL at the release tag, as `scripts/build-cli-readme.ts` does for the npm README. A link to a wiki page that does not exist fails the build. |
| Generated pages | A fact that lives in code is generated, never written by hand. `pnpm docs:generate` writes Markdown into `docs/wiki/generated/`, with a banner that names the script. The files are committed, so GitHub and agents read them too. `pnpm docs:check` regenerates in memory and fails on any difference, as `pnpm deps:check` does (grill Q2, asked). |
| Generated page URLs | `/docs/modules/email`, `/docs/env`, `/docs/cli`. The `generated/` folder does not appear in a URL (grill Q7, defaulted). |
| No pre-commit regenerate | CI runs `docs:check`. The `AGENTS.md` line tells an agent to run `docs:generate`. `lint-staged.config.js` keeps to formatting and lint (grill Q9, defaulted). |
| What is generated | The module catalog and one page for each module, the environment variable reference (`envVars`, `envServices`), the CLI command reference, the glossary (from `CONTEXT.md`) and the ADR index (from `docs/adr/`). `modules.md` and the generated parts of `reference.md` are replaced. |
| A module page | The descriptor facts, then the module's full skill text from `modules/<name>/skills/*/SKILL.md` under the heading "What your agent reads", with the skill's relative links rewritten like wiki links (grill Q3, asked). A script writes it, so it costs no second edit, which answers wikikit's rule against mirror pages. |
| Content loaders under `astro dev` | Phase 3 starts with a spike: do the content loaders and the build-time `git` calls work while the Cloudflare adapter renders in workerd? If not, `scripts/docs-generate.ts` also writes a gitignored JSON that the site imports (grill Q8, defaulted). |
| Freshness source | `.wikimap.yaml` `documents:` globs and the existing provenance stamp. `scripts/docs-freshness.ts` lists each hand-written page whose covered paths changed after its stamp commit. No new metadata format. |
| Freshness in a pull request | One sticky PR comment that the `site` job writes and updates, plus the job summary. It lists each page whose covered paths the PR changes while the page stays unchanged. A `docs: none` label marks the PR as needing no doc change, and the comment then says so. It never fails the job (grill Q4, asked). The job needs `pull-requests: write`. |
| Regular full audit | None for now. The owner decides after a month of PR comments, on or after 2026-12-19 (grill Q5, asked). |
| Agent rule | `AGENTS.md` gets one convention line: a change to a path in `.wikimap.yaml` checks the pages that cover it in the same PR, and a descriptor change runs `pnpm docs:generate`. |
| Agent-readable output | Each page is also served as raw Markdown at `/docs/<slug>.md`, and the site serves `/llms-full.txt` with every page in order. `/llms.txt` gains a link to it (grill Q11, defaulted). |
| Search | Pagefind, run on `dist/client` after `astro build`. Static, no service, no key (grill Q10, defaulted). |
| Gates | `gate:a11y` and `gate:lighthouse` add `/docs`, one hand-written page and one generated module page to their route lists. The 95 Lighthouse floor holds for docs pages too. |
| Tests | Node's built-in test runner beside the source, as `apps/web/src/lib/module-catalog.test.ts` and `scripts/*.test.ts` already do. No new runner. |
| Page stamps | Phase 7 stamps each verified page in its PR, with the PR's last verified commit. This repo merges with merge commits, so that SHA stays reachable on `main` (grill Q21, defaulted). |
| Approved outward actions | An unattended build may run `gh label create "docs: none" --repo mimukit/saasaloy --description "This PR needs no docs change"`, and the PR shows the `gh label list --search "docs: none"` output as proof (grill Q18, asked, 2026-11-19). The Phase 1 mockup images go to the `mockups: mimukit/saasaloy` gist under the owner's standing rule. The production deploy runs only inside a release the owner starts. |
| UI house rules this plan follows | From `apps/web/DESIGN.md`: square corners, no shadow, glow or gradient, Geist for prose and Geist Mono for every command, module name, path and env value, semantic tokens only, `primary` never at body size in dark, links that leave the site open in a new tab through `externalLinkProps`, light and dark theme toggle only, motion at or under 200ms from the named utilities, no value in copy that goes stale. New for this plan: the sidebar and the table of contents use hairlines and tonal surfaces, never a card shadow. The version label in the docs header is not stale copy, because the build reads it. |

## Approach

The site reads the wiki where it lives, generates every list and table from the files that own the facts, measures the age of every hand-written page against the code it covers, and publishes with each CLI release. It reuses:

- `apps/web/src/layouts/Layout.astro`, the navbar, the footer, `brand.css` and `web.css` for the frame and the tokens.
- `apps/web/src/lib/module-registry.ts` and `module-catalog.ts`, which already read every descriptor at build time.
- `docs/wiki/.wikimap.yaml` for the page list and the covered paths, and the wikikit provenance stamp for the verified commit.
- `scripts/build-cli-readme.ts` for the relative link rewrite, and `scripts/llms-txt.ts` with `scripts/release-preflight.ts` for the link and name checks.
- `apps/web/src/pages/llms.txt.ts` for the raw text route pattern, and `sitemap.xml.ts` for the page list.
- `.github/workflows/site.yml`, which already runs on `docs/wiki/**` and `modules/**`.
- `scripts/update-deps.ts --check` as the shape of a generate script with a check mode.
- `packages/cli/.release-it.js` and the `deploy:production` script in `apps/web/package.json` for the release deploy.

Rejected: generate pages only inside the site build. GitHub and agents in the repo would then lose `modules.md`. Rejected: front matter `covers:` in each page. `.wikimap.yaml` already holds the same globs.

### Phase 1: approve the docs mockup

Attended: the owner approves the mockup screenshots in this planning session (grill Q22).

- Mock up four screens in light and dark, at 375 px and 1440 px: a hand-written page (`how-to/add-a-module`), a generated module page (`email`), the module catalog page with the graph block, and the search dialog.
- Each screen shows the sidebar with its groups, the page header with the version label and the verified line, the table of contents, a code block with a copy button, and the previous and next links. One screen also shows the "Built from `main`" banner.
- Proposed sidebar groups: Start, Build with an agent, Modules, Guides, Runbooks, Reference, Decisions. The mockup settles them (grill Q12).
- Upload the images to the `mockups: mimukit/saasaloy` gist and show them in chat. Post the approved round to the tracking issue when issuekit files it.
- Record the approval as a "Mockup approved" Design decisions row with the date, the round, and the gist URL with the file prefix.

Done when: this plan has a "Mockup approved" row that names the date, the round and the gist file prefix.

### Phase 2: generated reference pages

- Add `scripts/docs-generate.ts`, with `pnpm docs:generate` and `pnpm docs:check` in the root `package.json`.
- It writes `docs/wiki/generated/modules.md` (the catalog table), `docs/wiki/generated/modules/<name>.md` for each module, `env.md`, `cli.md`, `glossary.md` and `adr.md`. Each file starts with a banner that names the script and says not to edit it.
- A module page holds the tier, the description, `dependsOn`, `requiresOneOf`, `conflictsWith`, each env var with its services, the files and workspaces it writes, its providers or drivers, and `saasaloy add <name> --dry-run` as the command that prints the rest. Then it holds the full skill text under "What your agent reads".
- Replace `docs/wiki/modules.md` with a short page that links to the generated catalog. Move the hand-written prose of `reference.md` that the generated pages now cover into links to them.
- Add `.wikimap.yaml` entries for the generated pages with `generated: true`. The freshness check skips them, because `docs:check` covers them.
- Add `pnpm docs:check` to `ci.yml`.
- Add the `AGENTS.md` convention line.
- Add `scripts/docs-generate.test.ts`: the catalog lists every folder in `modules/`, a descriptor change changes the output, a module page holds its skill text, and the check mode fails on a stale file.

Done when: `pnpm docs:check` passes, `docs/wiki/generated/modules.md` lists 56 modules, and changing one `description` in a descriptor makes `pnpm docs:check` exit non-zero.

### Phase 3: the /docs route

- Start with the spike from the "Content loaders under `astro dev`" row, and record the result in the PR.
- Add a `docs` content collection in `apps/web/src/content.config.ts` that reads `../../docs/wiki/**/*.md` with the `glob` loader.
- Add `apps/web/src/pages/docs/[...slug].astro` and `DocsLayout.astro`: the sidebar from `.wikimap.yaml`, the page, the table of contents from the headings, and previous and next links. `index.md` renders at `/docs`, and generated pages render without `generated/` in the URL.
- Add the remark plugin for links, and fail the build on a link to a missing wiki page.
- Add `apps/web/src/pages/docs/[...slug].md.ts` for the raw Markdown and `apps/web/src/pages/llms-full.txt.ts`. Add the `/llms-full.txt` link to the root `llms.txt`.
- Add the docs routes to `sitemap.xml.ts`.
- Point the navbar's Docs and Guide links and the catalog's module links in `landing.ts` at `/docs/...`.
- Add Pagefind to the build and a search control in the docs header.
- Add `/docs` and two docs pages to the route lists in `gate-a11y.ts` and `gate-lighthouse.ts`.

Done when: `pnpm --filter @saasaloy/web build` writes `dist/client/docs/index.html` and one HTML page for each wiki page and each generated page, `/docs/getting-started.md` returns the wiki file, `astro dev` renders `/docs/modules/email`, and `gate:a11y` and `gate:lighthouse` pass with the docs routes in their lists.

### Phase 4: interactive blocks

- Add the remark plugin that turns a `saasaloy-*` fenced block into an island, and fail the build on an unknown language.
- Add `saasaloy-graph`: the module dependency graph from the descriptors. A reader selects a module to see what it depends on, what depends on it, and its providers or drivers. The block takes an optional `focus=<module>`.
- Add `saasaloy-providers`: one capability and its provider modules, with the env var that selects one, drawn in the style of the landing providers illustration.
- Use the graph block on `architecture.md` and on the generated catalog page, and the providers block on each capability page.
- Each block renders the same facts as a plain list when JavaScript is off.

Done when: the catalog page shows the graph, selecting `email` shows `api` as its dependency and its three providers, and the page passes `gate:a11y` with JavaScript on and off.

### Phase 5: freshness checks

- Add `scripts/docs-freshness.ts` with `pnpm docs:freshness`. For each hand-written page in `.wikimap.yaml`, it lists the commits after the page's stamp that touched a covered path. `--base <ref>` limits it to a PR's diff.
- Add `scripts/docs-names.ts`, built on `scripts/llms-txt.ts`: every command, flag, module name and env var a wiki page names in backticks must exist. It runs in `pnpm test:scripts`.
- Create the `docs: none` label with `gh label create`, as the approved outward action allows.
- In `site.yml`, run `pnpm docs:freshness --base origin/main`. Write the result to the job summary and to one sticky PR comment that later runs update. With the `docs: none` label, the comment says the PR needs no doc change. Give the job `pull-requests: write`.
- Show the stamp on each page as "Verified against <short sha>", linked to the commit, beside the version label.

Done when: a test PR that changes `packages/cli/src/commands/add.ts` and not `how-to/add-a-module.md` gets one comment that names that page, a second push updates the same comment, the `docs: none` label changes its text, and the PR shows the `gh label list` output.

### Phase 6: the version label and the release deploy

- At build time, read the version from `packages/cli/package.json` and show it in the docs header. When `git describe --exact-match --tags --match "v*"` finds no tag at `HEAD`, show the "Built from `main`, N commits after v<latest>" banner.
- Add an `after:release` hook to `packages/cli/.release-it.js` that runs `pnpm --filter @saasaloy/web run deploy:release -- v<version>`. Add that script: it builds the site and runs `wrangler deploy --tag v<version> --message "saasaloy v<version>"`.
- On failure, the hook prints the rerun command from the "A deploy hook that fails" row and exits non-zero.
- Add the release deploy to the release steps in `CONTRIBUTING.md`.

Done when: `pnpm release:dry` prints the deploy hook and deploys nothing, a build at a `v*` tag shows no banner, a build on `main` shows the banner with the right count, and `pnpm --filter @saasaloy/web exec wrangler deploy --dry-run` passes.

### Phase 7: verify the hand-written pages

- Run wikikit `update` on the 11 hand-written pages, and fix every claim that changed after `42cbf03`.
- Stamp each verified page in the PR with the PR's last verified commit.

Done when: `pnpm docs:freshness` lists no page, `pnpm docs:check` passes, and the generated catalog lists 56 of 56 modules.

## Open questions

None. Every question from the draft was settled in the grill on 2026-11-19. Nothing is deferred.

## Non-goals

- The live codebase tour and the example SaaS walkthrough. They get their own plan and issue, which build on this plan's layout and generated data.
- Runnable examples, a `sh run` block that CI runs in `.dev/`. A later plan (grill Q6).
- A regular full docs audit by an agent. The owner decides on or after 2026-12-19 (grill Q5).
- A CI deploy, and a preview deploy of `main`. The release hook is the only path to production.
- A per-page "unreleased" marker.
- Versioned docs, one copy per release.
- Translations.
- A docs engine (Starlight, Docusaurus, VitePress).
- MDX in `docs/wiki/`.
- Moving `docs/adr/`, `docs/plans/` or `CONTEXT.md` into the site as pages. The site links to them on GitHub, and only the generated ADR index and glossary appear as pages.
- Comments, ratings or analytics on doc pages beyond the existing cookieless beacon.
