# Plan: `billing` capability with `billing-stripe`, `billing-console` and `entitlements`

Grilled: 2026-09-08

Issue: [#126](https://github.com/mimukit/saasaloy/issues/126). Source: `docs/plans/plan-module-catalog-2026-09-07.md` (P0 #3 and #4), `docs/research/research-module-libraries-2026-09-07.md`. Supersedes #14. Blocked by #125 (`queue`).

## Context

Every monetisation feature in the catalog waits on billing, and the catalog settled two things already: `billing` splits into a neutral core plus provider modules from day one, and `entitlements` is its own module because a free plan needs a plan-to-feature map with no payment provider installed. This plan builds four modules: `billing` (the core, `packages/billing`), `billing-stripe` (the default provider, built on `@better-auth/stripe`), `billing-console` (the local provider) and `entitlements` (a feature over the core's table). It folds the Stripe half of `webhooks-in` into the provider, and carries `trials` and `dunning` as queue jobs in the last phase.

The capability follows the `email` shape (AGENTS.md "portable capabilities, swappable providers") and the fresh `queue` precedent (`docs/plans/plan-queue-capability-module-2026-09-08.md`): a vendor-blind core, one provider file registered through `plugin-array`, `BILLING_PROVIDER` selecting at runtime, and a local provider so a project runs checkout with no Stripe account.

Success means: `saasaloy add billing billing-stripe entitlements` produces a project where a signed-in user starts a Stripe Checkout from the admin app, returns, and sees an active subscription; a Stripe webhook updates the subscription row and its side effects run on the queue; `hasFeature("x")` answers from the project's own table; `BILLING_PROVIDER=console` runs the same routes with no network; and `billing-polar` needs one file, two `plugin-array` patches and one `package-json-dependency` patch.

Facts checked on 2026-09-08. `stripe` is at 22.6.1 with zero dependencies and a `worker` export condition. `@better-auth/stripe` is at 1.7.3 and peers on `better-auth ^1.7.3`; `modules/auth` pins 1.7.2 and bumps first. The plugin owns a `subscription` table and a `stripeCustomerId` column on `user` (and on `organization` when enabled), mounts `/subscription/upgrade|list|cancel|restore|billing-portal` and `/stripe/webhook` under the auth base path, takes `referenceId` with `customerType: "organization"` behind an `authorizeReference` callback, handles `checkout.session.completed` and `customer.subscription.{created,updated,deleted}` synchronously with an upsert by subscription id, forwards every Stripe event to `onEvent`, and lets a project rename the model and every field through `schema.subscription`. ADR 0033 (system-of-record test) exists on the #125 branch, not yet on `main`.

## Design decisions (settled)

| Decision | Resolution |
|----------|-----------|
| Providers, not drivers, and why the table does not decide it | The vendor holds the customer, the payment method and the subscription. `billing_subscription` is a projection of that record, written from webhooks and keyed by the provider's ids. ADR 0033's first question ("does the project own the schema?") is yes, its second ("would a swap move data?") is no: a swap re-subscribes customers, because a payment method never moves between vendors. The second question wins, as ADR 0033 says. ADR 0034 records this and adds a `billing` row to ADR 0033's table. |
| `@better-auth/stripe` is the Stripe provider's engine | Grilled and chosen over the raw SDK. The plugin owns customer creation, checkout, portal, cancel and restore, and the webhook state write. The provider file wraps it so the core, the routes and `entitlements` never name Stripe. Better Auth has plugins for Polar, Dodo and Autumn, so the next providers take the same shape. |
| One core table, and the plugin writes it | `billing_subscription` lives in the capability with vendor-blind columns: `id`, `referenceId`, `customerType`, `plan`, `status`, `providerSubscriptionId`, `providerCustomerId`, `providerScheduleId`, `seats`, `cancelAtPeriodEnd`, `cancelAt`, `canceledAt`, `endedAt`, `trialStart`, `trialEnd`, `metadata`, plus core-only `lockedAt` and `reminderSentAt`. `user.billingCustomerId` (and `organization.billingCustomerId` when `teams` is installed) is the customer link. `stripeAuthPlugin()` maps the plugin onto these names through `schema.subscription.modelName` and `fields`. `billing-console` writes the same table. Two dialect files under one target with `onlyWith`, as `auth` does. Migrations are generated by the project, never shipped. |
| The dependency runs `auth` → `billing`, never back | `packages/auth` gains `@repo/billing`. `packages/billing` never imports `@repo/auth`. One provider file `@billing/providers/stripe.ts` exports `stripeBilling()` (the contract) and `stripeAuthPlugin()` (the plugin factory). `stripe` and `@better-auth/stripe` land in `packages/billing/package.json`, with `better-auth` declared as a peer dependency there so the plugin resolves. |
| Contract methods take a `HostContext` | `{ headers: Headers; auth: unknown }`, supplied by the route in `apps/api`, which imports both packages. The Stripe provider casts `auth` and calls `auth.api.upgradeSubscription`, `cancelSubscription`, `restoreSubscription` and `createBillingPortal` inside the plugin's own validation and `authorizeReference`. A provider never re-implements the plugin's checkout metadata. |
| The webhook is the plugin's, and side effects run on the queue | Stripe posts to `/auth/stripe/webhook`. The plugin verifies the signature, upserts the row and answers. `onEvent` maps the Stripe event onto a normalized `BillingEvent` and enqueues `billing.event`. The consumer inserts `(provider, providerEventId)` into `billing_event` and skips on conflict, so a redelivered event never sends a second email. The issue's "webhook handling is a queue consumer" reads as "webhook side effects are a queue consumer". |
| Normalized events and statuses | Event types: `subscription.changed`, `subscription.deleted`, `trial.ending`, `payment.failed`, `payment.succeeded`. Statuses: `trialing`, `active`, `past_due`, `canceled`, `unpaid`, `incomplete`, `paused`. A provider maps its own set and keeps the raw value in `metadata`. Unmapped vendor events are dropped in `onEvent`. |
| Plans are defined in code | `packages/billing/src/plans.ts` exports `plans = definePlans([...])`. A plan carries `id`, `name`, `features` (booleans), `limits` (numbers), `trialDays?`, and `providerIds` mapping a provider name to its price ids per interval. The default plan has no `providerIds`. `stripeAuthPlugin()` maps this list into the plugin's shape: `providerIds.stripe.monthly` → `priceId`, `.yearly` → `annualDiscountPriceId`, `trialDays` → `freeTrial.days`, `limits` passed through, `features` core-only. No seeded table. |
| The billable subject is opaque, and one file owns it | `@billing/subject.ts` exports `resolveSubject(c)` and `authorizeSubject(user, subject, action)`. The default bills the user and allows only `referenceId === user.id`. `teams` ships an organization version of the same file under `onlyWith`, with a membership check. `stripeAuthPlugin()` wires `authorizeSubject` into `authorizeReference`. |
| The customer is created at first checkout | `createCustomerOnSignUp: false`. No Stripe call in the signup path. |
| One live subscription per subject | `POST /billing/checkout` refuses with `invalid_request` when a live subscription exists and points at the portal. The table keeps history rows. Add-ons are a later issue. |
| `past_due` keeps the paid plan until lockout | `billing.past-due-lockout` runs daily and sets `lockedAt` on rows `past_due` for more than `BILLING_LOCKOUT_DAYS` (default 14). `payment.succeeded` clears it. A locked subject resolves to the default plan. |
| The screen lives in `apps/admin` | A `/billing` page: current plan and status, plan picker posting to `/billing/checkout`, "Manage billing" to `/billing/portal`, invoice list. `const-array` on `NAV_ITEMS`, as `teams` does. `billing` adds `admin` to `dependsOn`. |
| Pricing block keeps its own copy | The base's `pricing-table` reads `content/landing.ts`. No patch from `plans.ts`; the skill states that the two must be kept in step by hand. |
| `entitlements` reads the table and the plan file, no `kv` | `hasFeature`, `limit` and `currentPlan` take `(db, subject)`, do one indexed read, memoize in `c.var` for the request, and fall back to the default plan. `invalidateEntitlements(subject)` is a no-op hook the consumer already calls; `kv` caching is a follow-up after #129. |
| Seats are a follow-up issue | The contract ships `setQuantity` (the plugin's `seats` on upgrade). The `teams` member hook and the seat cap are their own issue, after `teams` drops its `database-d1` pin. |
| `billing_event` is not pruned | A few rows per subscription per month. The skill states the growth rate. |
| Error codes | `BillingError` codes: `invalid_request`, `not_found`, `card_declined`, `rate_limited`, `webhook_invalid`, `provider_error`. Providers map vendor codes, keep the raw one in `providerCode`, set `retryable` honestly. The core never retries. |
| Zero npm runtime dependencies in the core | `packages/billing` depends on `@repo/db` and `@repo/queue` (workspace) and on no npm package. The vendor packages enter through the provider's `package-json-dependency` patch (ADR 0020). |

## Approach

Reuses, by name: `modules/email/files/src/{define,provider,index}.ts` as the core template; `modules/queue/files/src/{define,provider}.ts` from the #125 branch for `defineJob` and `defineSchedule`; `modules/auth/files/db/schema/auth.{sqlite,pg}.ts` and `onlyWith` for the two-dialect table; `modules/auth/skills/saasaloy-auth/SKILL.md` "plugin-array patch point" for the `auth.plugins` registration; `modules/teams/files/auth/plugins/organization.ts` as the precedent for a module feeding a Better Auth plugin; `packages/cli/src/lib/patch/ts-module.ts` (`plugin-array`) for provider, plugin and job registration; `chained-route` (ADR 0028) for the typed billing routes; `const-array` on `NAV_ITEMS` for the admin page; `.agents/skills/create-provider/SKILL.md` gains a `billing` mode.

Rejected alternatives, one line each:

- Raw `stripe` SDK with core-owned checkout and webhook. More vendor code to write and maintain, and the next three providers all ship Better Auth plugins already.
- Drivers (`conflictsWith`, one installed). Loses `billing-console` beside `billing-stripe`, the reason the shape exists.
- Thin core with provider-owned storage. The admin page would call `authClient.subscription.upgrade`, a Stripe-shaped client API, and Polar would need a second page.
- Two tables, the plugin's own mirrored into a core projection by hooks. Every row twice and a sync bug class.
- Two runtime files per provider with a package cycle. Vendor deps in two workspaces and a cycle `pnpm` only warns about.
- SDK-direct checkout with the plugin only for the webhook. The provider must reproduce the metadata the plugin's handler expects and breaks on a plugin upgrade.
- Core-owned webhook route that replays into the plugin. The plugin exposes no "apply this event" entry.
- Plan-to-feature map in a seeded table. Needs an admin editor and a seed step before it beats a typed file.
- `entitlements` inside `packages/billing`. The catalog settled the split.

### Phase 1: ADR, auth bump and the neutral core

- [ ] Write ADR 0034 "Billing tables are a projection of the vendor's record": states why `billing` takes providers under ADR 0033's second question, adds the `billing` row to that ADR's table, states that a swap re-subscribes customers, and records the `auth` → `billing` dependency direction with the `HostContext` consequence. Adds `CONTEXT.md` entries for "Plan", "Subscription", "Billable subject", "Entitlement" and "Projection table".
- [ ] Bump `better-auth` to 1.7.3 in `modules/auth/files/package.json` through `pnpm deps:update`, so `@better-auth/stripe` 1.7.3 resolves its peer.
- [ ] `modules/billing/registry-item.json`: `saasaloy:capability`, `dependsOn: ["api", "database", "auth", "admin", "queue"]`, `envVars.BILLING_PROVIDER` (required), `BILLING_LOCKOUT_DAYS` (default 14), scaffold `packages/billing` with alias `@billing`, `package-json-dependency` `@repo/billing` into `apps/api` and into `packages/auth`.
- [ ] `files/db/schema/billing.sqlite.ts` and `billing.pg.ts` → `@db/schema/billing.ts` with `onlyWith`: `billing_subscription` with the columns above (unique on `providerSubscriptionId`, index on `referenceId`) and `billing_event` (`provider`, `providerEventId` as the primary key, `type`, `receivedAt`, `processedAt`). `files/db/schema/user-billing.{sqlite,pg}.ts` adds `billingCustomerId` to `user`.
- [ ] `provider.ts`: `BillingProvider` (`name`, `createCheckout`, `createPortal`, `changePlan`, `cancel`, `restore`, `setQuantity`, `listInvoices`, `authPlugin?`), `HostContext`, `BillingEnv` (opaque, `BILLING_PROVIDER?`), `Plan`, `Subscription` (the row shape), `BillingEvent`, `CheckoutResult { url, event? }`, `Invoice`, `BillingError` with the six codes.
- [ ] `define.ts`: `defineBilling({ providers })` with `create(env)` selecting on `BILLING_PROVIDER`, unset or unknown throws listing registered names, raw throws wrapped as `provider_error`. `definePlans`.
- [ ] `plans.ts` with a `free` default and one `pro` example, `providerIds: {}` to fill. `subject.ts` with the user-only `resolveSubject` and `authorizeSubject`. `index.ts` barrel with `billing = defineBilling({ providers: [] })`, `createBilling(env)`, `plans`, `src/providers/.gitkeep`.
- [ ] `subscription.ts`: `currentSubscription(db, subject)` (latest live row) and `applyEvent(db, event)` for the console path and the consumer (`billing_event` insert-or-skip, `lockedAt` and `reminderSentAt` updates, `invalidateEntitlements`).
- [ ] `package.json` exports `.`, `./providers/*`, `./plans`, `./subject`; `clean` with pinned `rimraf`. Unit tests: selection, `BillingError` wrapping, `applyEvent` on each event type and on a replayed event.

### Phase 2: routes, the consumer and the admin page

- [ ] `files/api/routes/billing.ts` → `apps/api/src/routes/billing.ts`, registered by `chained-route` on `app`: `POST /checkout` (planId, interval, successUrl, cancelUrl), `POST /portal` (returnUrl), `GET /subscription`, `POST /cancel`, `POST /restore`, `POST /change-plan`, `GET /invoices`. Each runs behind the session, calls `resolveSubject`, builds a `HostContext` from the request headers and the `auth` instance, and runs inside `withAuthScope` (ADR 0029). `POST /checkout` refuses when a live subscription exists.
- [ ] `@billing/jobs/event.ts` exporting `billingEventJob()`, registered into `queue.jobs` by `plugin-array`. The handler calls `applyEvent`. A `not_found` on the row is `retryable: true` for a checkout race.
- [ ] The console path: `POST /checkout` enqueues `result.event` when present, before returning the url.
- [ ] `apps/admin` page `/billing` and its `const-array` NAV entry.
- [ ] `saasaloy-billing` skill: contract, `HostContext`, the subject file and what `teams` overrides, the plan file and the pricing block rule, the webhook URL to register in Stripe and the events to subscribe (`checkout.session.completed`, `customer.subscription.created|updated|deleted|trial_will_end`, `invoice.payment_failed`, `invoice.paid`), `billing_event` growth, how to write a third provider.

### Phase 3: `billing-stripe` and `billing-console`

- [ ] `modules/billing-stripe`: `files/stripe.ts` → `@billing/providers/stripe.ts` exporting `stripeBilling()` and `stripeAuthPlugin()`. Patches: `plugin-array` `stripeBilling` into `billing.providers`; `plugin-array` `stripeAuthPlugin` into `auth.plugins` from `@repo/billing/providers/stripe`; `package-json-dependency` `stripe@22.6.1` and `@better-auth/stripe@1.7.3` into `packages/billing/package.json`, `better-auth` as a peer. `envVars` `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`. No wrangler binding.
- [ ] `stripeAuthPlugin()` reads `env` from `cloudflare:workers` as `auth.ts` does, builds the `Stripe` client, maps `plans` into the plugin shape, maps `schema.subscription` onto `billing_subscription` and `user.billingCustomerId`, sets `createCustomerOnSignUp: false`, wires `authorizeSubject`, and in `onEvent` maps `customer.subscription.*`, `customer.subscription.trial_will_end`, `invoice.payment_failed` and `invoice.paid` onto the normalized events and enqueues `billing.event`.
- [ ] Verify at build that the `fields` map covers every plugin column, and that the plugin's own field set has not grown since 1.7.3. Record the checked column list in the skill.
- [ ] `stripeBilling()`: `createCheckout` → `auth.api.upgradeSubscription` with `referenceId`, `customerType`, `plan`, `annual`, `seats`; `createPortal` → `createBillingPortal`; `cancel` and `restore` → the plugin's endpoints; `changePlan` and `setQuantity` → `upgradeSubscription` with `subscriptionId`; `listInvoices` → the SDK's `invoices.list` mapped to `Invoice` with `hostedInvoiceUrl` and `pdfUrl`.
- [ ] Error mapping: `card_error` → `card_declined`, `rate_limit_error` → `rate_limited` retryable, `invalid_request_error` and plugin `APIError` 4xx → `invalid_request`, else `provider_error`.
- [ ] `modules/billing-console`: `files/console.ts` → `@billing/providers/console.ts` exporting `consoleBilling()`, one `plugin-array` patch, no auth plugin. Ids are `console_<random>`; `createCheckout` writes an `active` (or `trialing` when the plan has `trialDays`) row and returns `successUrl` plus a synthetic `subscription.changed` event; `createPortal` returns `returnUrl`; `cancel`, `restore`, `changePlan` and `setQuantity` update the row; `listInvoices` returns an empty list.
- [ ] `.agents/skills/create-provider/SKILL.md` gains a `billing` mode. End-to-end in `.dev`: `saasaloy add billing billing-stripe entitlements` typechecks; `stripe listen --forward-to` completes a checkout and the row appears; `BILLING_PROVIDER=console` completes the same flow with no network; `saasaloy remove billing-stripe` leaves `index.ts`, `auth.ts` and `package.json` byte-identical.

### Phase 4: `entitlements`

- [ ] `modules/entitlements`: `saasaloy:feature`, `dependsOn: ["billing"]`, no provider required at runtime. File `@billing/entitlements.ts` exporting `hasFeature(db, subject, name)`, `limit(db, subject, name)`, `currentPlan(db, subject)` and `invalidateEntitlements(subject)`.
- [ ] Resolution rule: the latest row for the subject whose status is `trialing`, `active` or `past_due` and whose `lockedAt` is null selects the plan; otherwise the default plan. Memoized per request in `c.var`.
- [ ] A Hono middleware `requireFeature(name)` for `apps/api` routes, returning 402 with the feature name.
- [ ] Tests over `queue-memory` and `billing-console`: a free subject has no `pro` feature; after a console checkout it does; after `subscription.deleted` it does not; a locked subject resolves free.
- [ ] `saasaloy-entitlements` skill: the plan file is the source of truth, the resolution rule, the 402 middleware, and that caching arrives with `kv`.

### Phase 5: trial and dunning side effects

- [ ] `trial.ending` (from Stripe's `customer.subscription.trial_will_end`, three days before) sends `trialEndingTemplate` through `createEmail` and sets `reminderSentAt`, once per subscription. Adds `email` to `billing`'s `dependsOn`. No daily trial scan.
- [ ] `payment.failed` sends `paymentFailedTemplate`. `@billing/jobs/past-due-lockout.ts` runs daily by `defineSchedule`, sets `lockedAt` on `past_due` rows older than `BILLING_LOCKOUT_DAYS`, and sends `accountLockedTemplate`. `payment.succeeded` clears `lockedAt`.
- [ ] The job registers into `queue.jobs` and `queue.schedules` by `plugin-array`. Three email templates in `@email/templates/`.
- [ ] File the follow-up issues from this plan: `seats` (`teams` member hook, seat cap, after the `database-d1` pin drops), `kv` cache for entitlements (after #129), `billing-polar` as the second provider that proves the contract, add-on subscriptions, and the generic `webhooks-in` receivers (GitHub, HMAC).

## Open questions

None left open by the grill on 2026-09-08. One check is deferred to the build, not to a decision: that `schema.subscription.fields` in `@better-auth/stripe` 1.7.3 covers every column the plugin writes (Phase 3).

## Non-goals

- A plan-to-feature table with a seed step or an admin editor.
- Seat counting from `teams` members and a seat cap. Follow-up issue.
- `kv` caching of entitlements. Follow-up after #129.
- `billing-polar`, `billing-lemonsqueezy`, `billing-paddle`. The contract must admit them; this plan builds none.
- A second live subscription per subject (add-ons).
- Usage metering, coupons, tax, one-time purchases, marketplace payouts.
- Generic inbound webhooks for GitHub or HMAC. A later `webhooks-in` module.
- Pruning `billing_event`.
- Migrating live subscriptions between providers. A swap re-subscribes.
- Stripe Customer Portal configuration, Stripe Tax and Stripe Billing emails. The project configures those in the Stripe dashboard; the skill says so.
