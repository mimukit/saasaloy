# Plan: `multitenant`, `rbac` and `api-keys`

Grilled: 2026-09-09

Issue: [#128](https://github.com/mimukit/saasaloy/issues/128). Source: `docs/plans/0048-plan-module-catalog-2026-09-07.md` (P0 #10 and #11, the `tenant-scoping`, `rbac` and `api-keys` rows). Independent of #125, #126, #127 and #129.

## Context

`teams` shipped the `organization`, `member` and `invitation` tables and the active-organization switch. Nothing above it enforces a boundary. A route that reads `packages/db` today can select every row of a table no matter which organization the caller belongs to, and there is no helper that says which organization a request is for. `requireAdmin` (plan `0037-plan-admin-authorization-2026-08-31.md`) answers one question, "is this the site admin", and every B2B feature in the catalog needs three more: which tenant, what may this member do here, and how does a machine caller with no cookie get the same answers.

This plan builds those three as three feature modules in one dependency chain. `multitenant` resolves the tenant onto a request and guards the repository layer. `rbac` gives an organization runtime-defined roles with permission statements and a `can()` helper. `api-keys` adds a bearer credential that resolves the same tenant and passes through the same `can()`. No provider split, as the issue says: there is no vendor to swap, and the ADR 0033 test does not apply to in-house code over `database`, `auth` and `teams`.

The grill on 2026-09-09 changed two things the draft assumed. Roles are **dynamic**: a customer defines roles per organization at runtime through Better Auth's `dynamicAccessControl`, on top of a locked static base. And the site has two privileged user roles from now on: `superadmin`, who may act inside any organization through a header, and `admin`, who is a site admin for `apps/admin` and an ordinary member everywhere else.

Facts checked against Better Auth `v1.7.2` source on 2026-09-09. The API-key plugin is a separate package, `@better-auth/api-key`, at the same version. Its `apikey` table carries `configId`, `name`, `start`, `referenceId`, `prefix`, `key` (hashed), `refillInterval`, `refillAmount`, `lastRefillAt`, `enabled`, `rateLimitEnabled`, `rateLimitTimeWindow`, `rateLimitMax`, `requestCount`, `remaining`, `lastRequest`, `expiresAt`, `createdAt`, `updatedAt`, `permissions` (a JSON string) and `metadata`. `references: "organization"` makes `referenceId` an organization id, and then `create`, `get`, `update`, `delete` and `list` check the caller's membership and an `apiKey: [action]` permission through the organization plugin's own access control. `verifyApiKey` hashes the presented key with SHA-256, refuses a disabled or expired key with a 401 code, writes `lastRequest` on every call, and when the caller passes `permissions` it checks them with `role(key.permissions).authorize(permissions)`, the same engine `hasPermission` runs for a member. Session mocking from a key works for user-owned keys only.

The organization plugin's `defaultStatements` are `organization`, `member`, `invitation`, `team` and `ac`. With `dynamicAccessControl.enabled`, an `organizationRole` table appears: `id`, `organizationId` (FK to `organization`, indexed), `role` (indexed), `permission` (a JSON string), `createdAt`, `updatedAt`. `hasPermission` loads that organization's rows and merges each row's statements over the static role of the same name, so a stored role named `admin` extends the static `admin`. `createRole`, `updateRole` and `deleteRole` are gated by the `ac` statement, `deleteRole` does not check whether members still hold the role, `updateMemberRole` refuses a role name that exists in neither the static set nor the table, and the client's `checkRolePermission` knows static roles only. `maximumRolesPerOrganization` defaults to unlimited.

Success means: `saasaloy add api-keys` pulls in `multitenant` and `rbac`; a scoped route written with `requireTenant` and `forTenant` cannot return another organization's row on either driver; an owner creates a `viewer` role in the admin app, assigns it, and that member gets a 403 on `DELETE /projects/:id` and does not see the button; a key minted with `project: ["read"]` reads a scoped route over `Authorization: Bearer` and is refused on a write; revoking the key turns the next call into a 401; a `superadmin` reads any organization's projects with `x-organization-id`, and an `admin` sending the same header gets 403.

## Design decisions (settled)

| Decision | Resolution |
|----------|-----------|
| Three modules, one chain | `multitenant` depends on `api`, `database`, `auth`, `teams`. `rbac` depends on `multitenant` and `admin`. `api-keys` depends on `rbac`. The issue's Phase 4 requires keys to pass through `can()`, and `can()` needs the tenant, so the chain is linear and `saasaloy add api-keys` installs all three. |
| Two site roles: `superadmin` and `admin` (Q19, Q20, Q21) | `modules/auth` declares both. `admin({ adminRoles: ["admin", "superadmin"] })`, `SUPERADMIN_ROLE` beside `ADMIN_ROLE` in `authorize.ts`, `requireSuperadmin` exact, `requireAdmin` admits either. The first-user-wins hook writes `superadmin`; a later `admin` is granted through `setRole`. `apps/admin`'s guard admits both. Inside an organization an `admin` is an ordinary member: `requireTenant` resolves their active organization and their membership role, and the site role grants nothing on a tenant route. |
| Resolution is a throwing helper in `packages/auth`, not middleware | `requireTenant(c)` sits beside `requireAdmin` in `@repo/auth/server`. The `chained-route` patch kind registers routes, not `.use()` links (ADR 0028), and `api` cannot import `auth`. A throw reuses api's `onError` envelope. One call per route is the cost `requireAdmin` already charges. |
| The cookie path resolves from the session's active organization, verified by membership | `requireTenant` calls `auth.api.getActiveMember` inside `withAuthScope`. That reads the session and the `member` row for `session.activeOrganizationId` in one call, so a membership revoked after `setActive` fails closed on the next request. |
| The `superadmin` bypass (Q6, Q11, Q12, Q14) | `x-organization-id` is honoured on the cookie path only, and only when `session.user.role === "superadmin"`. The principal is `{ kind: "superadmin", userId }` and `can()` returns true for it, in one `switch` arm. Any other caller sending the header gets 403 `forbidden`. The header on the bearer path is 403 whatever it says: a key is bound to one organization. |
| The bearer path is a credential resolver table | `@auth/tenant.ts` exports `export const tenantResolvers = defineTenantResolvers({ resolvers: [] })`, a module-scope array literal for the `plugin-array` codemod, empty by default. A resolver claims a credential it recognises (a header) and returns a principal or throws. When no resolver claims the request, the session path runs. `api-keys` registers `apiKeyTenant` there. |
| One principal type, three kinds | `Tenant` is `{ organizationId, principal }` and `principal` is `{ kind: "member", userId, memberId, role, statements }`, `{ kind: "apiKey", keyId, statements }` or `{ kind: "superadmin", userId }`. A handler reads `tenant.organizationId`; `can()` reads `principal`. |
| Roles are dynamic on a locked static base (Q1, Q16, Q18) | `teams` enables `dynamicAccessControl` in `organizationPlugin()` and ships the `organizationRole` snapshot in two dialects. The static base is `owner`, `admin`, `member` in `@auth/access.ts`. Base roles are read-only: the `/roles` screen shows them without an edit or delete control, and a `roleLockGuard()` plugin refuses `createRole`, `updateRole` and `deleteRole` for a base name server-side, so nothing can extend `admin` by storing a row of the same name. Only custom roles are created, edited or deleted. Cap unlimited, the plugin default (Q15). |
| `requireTenant` loads the roles once, `can()` stays pure (Q8) | On the member path `requireTenant` reads that organization's `organizationRole` rows in one query and resolves the member's statements: the static role of that name merged with the stored row, or the stored row alone for a custom role, or empty when the name resolves to nothing. `can()` in `rbac-rules.ts` is a pure function over `principal.statements`, tested here under `node --test`. A route with three checks pays no extra query. |
| The permission vocabulary is static and seeded (Q2) | `teams` ships `@auth/access.ts`: `statements` (the plugin's `defaultStatements` plus `project: ["create", "read", "update", "delete"]` and `apiKey: ["create", "read", "update", "delete"]`), `ac = createAccessControl(statements)` and the three base roles. Owner and admin hold every statement; member holds `project: ["read"]` and `ac: ["read"]`. A custom role picks from these statements. The project adds a resource by editing this file, and no module patches it. |
| `teams` passes `ac` and `roles` on both sides | `organizationPlugin()` passes `{ ac, roles, dynamicAccessControl: { enabled: true } }`. A new `@auth/plugins/organization-client.ts` exports `organizationClientPlugin()` wrapping `organizationClient({ ac, roles })`, and the client patch call changes to it. |
| The SPA reads permissions from `GET /tenant` (Q17) | `multitenant` mounts `GET /tenant` by `chained-route`, returning the resolved `Tenant`. The admin screens fetch it once per page and run the same `can()` from `rbac-rules.ts` to hide a control. `checkRolePermission` is not used, because it cannot see a custom role. The hide is cosmetic; the 403 is the gate. |
| The repository guard is a branded id and one wrapper | `@repo/db/tenant` exports `TenantId` (a branded string), `forTenant(db, tenantId)` and `TenantTable`. `forTenant` returns `select(table)`, `insert(table, values)`, `update(table, set)` and `delete(table)` that append `eq(table.organizationId, tenantId)` and force `organizationId` on insert. Only `requireTenant` mints a `TenantId`. A table without an `organizationId` column does not fit `TenantTable`. Both are compile errors. Convention plus the skill enforce the wrapper's use in v1; a lint rule is a follow-up issue (Q5). |
| The tenant column convention | Drizzle property `organizationId`, column `organization_id`, `notNull`, `references(() => organization.id)`, one index. `member`, `invitation` and `organizationRole` already follow it. `apikey` follows it through the plugin's `schema.apikey.fields.referenceId` rename. `@repo/db/tenant-column` exports a `tenantColumn()` helper per dialect. |
| Keys are organization-owned, and a scope is a snapshot (Q10) | `apiKeyPlugin()` sets `references: "organization"`, `enableSessionForAPIKeys: false`, `rateLimit: { enabled: false }`, `keyExpiration.defaultExpiresIn: null`, `requireName: true`, `defaultPrefix: "sk_"`, `startingCharactersConfig.charactersLength: 8`. A key's `permissions` are fixed at issue time; editing a role later changes members and never keys, and the key list says so. |
| A key's scope cannot exceed its creator's statements | `apiKeyScopeGuard()` is a second Better Auth plugin in the same wrapper with a `before` hook on `/api-key/create` and `/api-key/update`. It resolves the caller's statements with the same loader `requireTenant` uses and refuses a `permissions` body that `authorize` would deny. |
| Last-used is a synchronous write (Q4) | `verifyApiKey` writes `lastRequest` on every bearer call. Accepted and documented; `ratelimit` (#129) is the answer for a hot key. `deferUpdates` stays off because its background task holds no `waitUntil` on Workers. |
| Failure codes (Q3) | Signed out is 401. Signed in with no active organization or no membership is 403 with the exported constant `NO_ACTIVE_ORGANIZATION` ("no active organization") as the message, which the SPA matches. A claimed bearer credential that fails is 401 `invalid api key`. A `can()` refusal is 403 `permission required: <resource>:<action>`. A forbidden `x-organization-id` is 403 `forbidden`. All render through api's `ERROR_CODES`. |
| The screens live in `apps/admin`, on the active organization (Q13) | `/roles` (rbac) and `/api-keys` (api-keys), each a `const-array` entry in `NAV_ITEMS`, each scoped to the caller's active organization behind the site-admin root guard, as `/teams` is. An organization picker over the bypass, and the all-organizations list route it needs, are a follow-up issue. |
| The worked example ships (Q7) | `multitenant` ships a `project` table and `/projects` routes. It is the table the isolation proof drives, the route `requireCan` gates, and the resource the key scope picker offers. Named in `removeWarnings`. |
| Exports are groundwork, not patches | No patch kind edits a `package.json` `exports` map. Phase 1 adds `./tenant` and `./tenant-column` to `modules/database/files/package.json` and `./tenant`, `./rbac` and `./access` to `modules/auth/files/package.json`. |
| The isolation proof is a type test plus a driver QA | The generated project ships no test runner, and `drizzle-orm` is not a dependency of this repo. `packages/db/src/tenant.typecheck.ts` carries `@ts-expect-error` lines that `tsc --noEmit` enforces. The runtime proof runs in `.dev` on both drivers. The import-free rule files get `node --test` coverage here, the `authorize.ts` precedent. |
| Removal | Each module declares `removeWarnings`. `teams` adds `organizationRole` to its list. `multitenant` names `project` and states that routes written against `requireTenant` stop compiling. `api-keys` names `apikey`. |

## Approach

Reuses, by name: `modules/auth/files/src/authorize.ts` and `server.ts` for the import-free rule file plus throwing helper split; `withAuthScope` and ADR 0029 for every `auth.api.*` call; `modules/teams/files/auth/plugins/organization.ts` and the `plugin-array` patch for the plugin wrappers; `modules/auth/files/src/client.ts`'s `definePlugins` for the resolver table's shape; `modules/auth/files/db/schema/auth.{sqlite,pg}.ts` and `onlyWith` for the two-dialect snapshots; `withDb` from `@repo/db/client` for the dialect-neutral query helper; `chained-route` for `/tenant` and `/projects`; `const-array` on `NAV_ITEMS` and `modules/teams/files/admin/components/organization-workspace.tsx` for the admin screens; `removeWarnings` for removal; `modules/admin/files/api/routes/admin-users.ts` as the route contract; the first-user-wins hook in `modules/auth/files/src/auth.ts` for the role change.

Rejected alternatives, one line each:

- Hono middleware on `base` for tenant resolution. No patch kind registers a `.use()` link, and `api` cannot import `auth`.
- Static-only roles. Chosen against in the grill: a customer cannot wait for a deploy to define a role.
- `auth.api.hasPermission` inside `can()`. One query per check and an impure `can()` nothing here can test.
- A bypass for the site `admin` role. Rejected in the grill: `admin` runs `apps/admin` and is a member everywhere else; only `superadmin` crosses organizations.
- The `owner` role's statements for the superadmin. Ties a backoffice power to a role a customer sees.
- User-owned keys with `enableSessionForAPIKeys`. The mock session carries no `activeOrganizationId`.
- A key that references a role name. The plugin stores statements only, and the guard would have to re-run on every role edit.
- An `after` hook that reassigns holders of a deleted role. A silent privilege change.
- A patchable `defineAccess({ statements: [...] })` shape. Real typing work for two seeded lines.
- `rbac` replacing `teams`'s wrapper to enable dynamic roles. Two modules owning one target.
- Row-level security in Postgres. D1 has none, and the guard has to be the same on both drivers.
- Extending `teams`'s member list with a role picker. That component belongs to `teams`.

## Non-goals
