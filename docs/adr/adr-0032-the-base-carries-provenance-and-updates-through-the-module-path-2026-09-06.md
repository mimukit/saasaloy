# 0032 — The base carries provenance and updates through the module path

`saasaloy init` copies the base template out of the CLI package and, until this record, wrote nothing down about what it copied. [ADR 0022](adr-0022-design-layer-ships-in-the-base-2026-08-06.md) called that a one-time gift: no manifest entry, no hash, no update path, on the grounds that blocks are meant to be edited and hash tracking would flag every project the moment it was used as intended. The gift held up for the design layer and failed everywhere else. The base is three workspaces, the lint and hook toolchain ([ADR 0023](adr-0023-generated-projects-ship-a-lint-and-hook-toolchain-2026-08-09.md)), the design contract ([ADR 0027](adr-0027-design-contract-ships-in-the-base-2026-08-28.md)) and the shipped agent skills. It is the largest body of code the tool generates and it was the only body the tool could not update, and `doctor`, `outdated` and `update` all told a scaffolded project that nothing was installed. Settled while grilling issue [#120](https://github.com/mimukit/saasaloy/issues/120); plan: [`plan-base-template-tracking-2026-09-06.md`](../plans/plan-base-template-tracking-2026-09-06.md).

**The base now records like a module and updates through the module engine.** `init` writes one `.saasaloy/manifest.json` entry per rendered file under the reserved module name `base`, hashed on the bytes that landed on disk, and a `base` object in `saasaloy-lock.json` holding `{ name, cliVersion, templateHash }`. `update` renders the bundled template for the project, hands it to the same classifier modules go through, overwrites what the owner never touched, and routes the rest into the merge plan. `outdated` shows the base as the first row and `doctor` reports which base files drifted. ADR 0022 is amended by this record, not replaced: the design layer is still in the base, and the files an owner is meant to rewrite are still not update targets.

## Status

accepted — amends the "one-time gift" consequence of [ADR 0022](adr-0022-design-layer-ships-in-the-base-2026-08-06.md); the rest of 0022 stands

## Considered Options

- **A version stamp only.** Write the CLI version into the lock and let `outdated` compare numbers. Rejected. It tells an owner that the template moved and leaves them to diff fifty files by hand, which is the work the tool exists to do. It is also blind: every CLI build is `0.0.0` until a release process exists, so a version compare would never turn the row red.
- **A commit SHA, like a module.** Rejected. The base ships inside the CLI package, so the project has no registry coordinate to re-resolve and no old commit to fetch a merge base from. A `templateHash` over the shipped template's sorted `(path, hash)` pairs answers the question the SHA answers for a module: did the thing I installed from change.
- **A three-way merge base.** Keep a copy of the rendered template under `.saasaloy/` at `init` so `update` can diff base to theirs and base to mine. Rejected for now. The existing `noMergeBase` two-way path already renders a plan an agent can act on, and the per-file hashes still separate a clean overwrite from real drift. If a true base is ever wanted, the path is that on-disk copy, never a network fetch.
- **Fingerprint an unrecorded project against every historical template.** Rejected. Adoption records the present. On an unrecorded project `update` hashes the base files as they stand, writes the record at the running CLI, and stops. The next run is a real update. It skips at most one generation of base changes and never produces a wall of false conflicts on a customised project.
- **Track the base in `saasaloy.json`.** Rejected. `saasaloy.json` is intent and the lock is what resolved ([ADR 0012](adr-0012-remote-first-registry-repo-is-the-registry-2026-07-23.md)). A template version is resolved state. `base` stays a plain name string there and `SaasaloyConfig` is untouched.

## Consequences

- **`ManagedEntry` and the manifest shape are unchanged.** Base files are ordinary managed entries with `module: "base"` and `from` set to the template-relative source path, `_gitignore` for `.gitignore`. Every engine that iterates `config.installed` keeps ignoring the base, because `base` is never in that list. `checkPartialInstalls` exempts the name so `doctor` does not read the record as a half-installed module.
- **Hashes are of rendered bytes.** `copyTemplate` substitutes `{{PROJECT_NAME}}` and `{{CLI_VERSION}}`, so the manifest records what landed and `update` renders the new template with the same vars before it compares. `templateHash` is the exception, hashed on source bytes, because it identifies the template and a project name must not change it.
- **Seed files are declared, recorded, and never updated.** `_saasaloy-base.json` in the template lists them as explicit paths: `DESIGN.md`, `README.md`, the landing copy in `packages/ui/src/content/landing.ts` and `apps/web/src/pages/index.astro`, and `saasaloy.json`, which the CLI itself rewrites on every `add`. `copyTemplate` skips the declaration by exact name before the `_` to `.` rename. `AGENTS.md` is managed: an untouched copy overwrites cleanly and an edited one goes through the drift path, so the shipped agent rules keep updating. `doctor` lists seed files as "seed, not checked".
- **`outdated` and `doctor` never write.** On a project with no record they report the base as `untracked` and point at `saasaloy update`. `outdated --check` does not exit 2 on `untracked`, so a CI checkout of an older project stays green. Only `update` adopts, and `update --dry-run` reports the adoption and writes nothing. A lock record with no manifest entries counts as untracked and re-adopts.
- **Downgrades are refused.** When the recorded `cliVersion` and the running one are both valid semver and the recorded one is higher, `update` prints both, says to upgrade the CLI, exits 2 and writes nothing. There is no override flag; `--yes` keeps its one meaning. An `unknown` version skips the check, as `cli-requires.ts` does.
- **A patched base file re-applies its patches after an overwrite.** `apps/web/package.json` is a base file that `waitlist` patches. When the template ships a new version of such a file and the owner never edited it, `update` writes the new render and runs every `manifest.patches` entry for that file through the idempotent re-apply loop it already runs for a module's own patches. A patch whose identity now holds a different value demotes the file to `drift` and the plan names the patcher.
- **Root `package.json` is a managed base file, so a run that overwrites it re-reads it before writing dependency pins.** The module engine used to hold the root `package.json` in memory across the whole run. A base overwrite of that file in the same run would have been clobbered by the stale copy.
- **The merge plan is the deliverable for drift.** Each drifted base file renders in the same Markdown `renderMergePlan` writes for modules, with a two-way diff from the current file to the new render and the intent line "the base template changed; keep local edits, take the upstream change". The section header states why there is no merge base.
- **The lock record moves only on a clean run.** As with a module, a run that leaves anything in the merge plan keeps the old `base` record so a re-run offers the same files again. A clean run rewrites the base's manifest entries and the lock record together.
