# 0022 — The design layer ships in the base

The base template owns a real design layer: Tailwind 4 plus a vendored set of shadcn primitives and marketing **blocks** in `packages/ui`, and a landing page in `apps/web` composed from them. This overrides [ADR 0003](adr-0003-base-is-landing-page-only-2026-07-22.md)'s "no Tailwind/React" clause — React had already landed in the base for module islands, so the base was paying React's cost while still rendering an unstyled placeholder. Everything else 0003 decided (nothing churny in the base; API, database, auth and features arrive via `add`) stands unchanged. Settled while grilling the UI-blocks plan; see [`docs/plans/plan-ui-blocks-2026-08-01.md`](../plans/plan-ui-blocks-2026-08-01.md).

## Status
accepted — overrides the "no Tailwind/React" clause of [ADR 0003](adr-0003-base-is-landing-page-only-2026-07-22.md); the rest of 0003 stands

## Considered Options
- **Ship the design layer as a module (`saasaloy add ui`)** — rejected: every generated project wants a styled landing page, so an opt-in module is a step everyone would take. Worse, it inverts the dependency — `waitlist` and every later feature module drop UI into a surface that might not exist, so each would have to declare `dependsOn: ["ui"]` for something with no capability of its own. The base is where a universal, non-churny surface belongs.
- **Keep the base literally unstyled and let each module bring its own CSS** — rejected: the first two modules would disagree about tokens, and there is no arbiter. One theme in `packages/ui` is the arbiter.
- **Inline (`eject`) the `shadcn` CLI's output and drop the `shadcn` dependency** — rejected: see the consequence below. A frozen copy is not more inert than an exact pin, and it silently drifts from the `shadcn/tailwind.css` any later `shadcn add` assumes.
- **`radix-nova` primitives** (what shadcn's own `astro-monorepo` template still ships) — rejected in favour of `base-nova`, which is what the shadcn docs now show everywhere. `style` cannot be changed after init, so this is a deliberate divergence from the upstream template, not an oversight.
- **Track base files in `.saasaloy/manifest.json` so they get an update path** — rejected: see the one-time gift below.

## Consequences
- **The inert thesis is narrowed, not refuted.** ADR 0003's anti-rot argument holds on *functional* surfaces: the base still has no services, no auth, no database, and no network dependency. Presentation dependencies rot **aesthetically, not dangerously** — a two-year-old Tailwind theme looks dated, it does not leak sessions or break a deploy. That asymmetry is the whole reason a design layer is allowed in the base while auth still is not.
- **`base-nova` is a bet, and the escape hatch is on the template side.** Initted projects are insulated by construction: the primitives are vendored source and every dependency is exact-pinned, so upstream churn cannot break a project retroactively. Blocks never expose the primitive family in their prop types, so if Base UI churns badly the template swaps families in a future release — a contained rewrite of `packages/ui/src/components/` affecting only *new* inits. The cost of the bet lands solely on template maintenance at `deps:update` time.
- **Base files are a one-time gift, by design.** `init` stays a pure copy: base files get no manifest entries, no content hashes, and therefore no `--diff` update path. Blocks are you-own-the-code source *meant* to be edited, so hash-drift tracking would flag every project the moment it was used as intended. Upgrading the design layer of an existing project is a manual, opt-in job — never something the CLI offers to do.
- **`shadcn` stays a live runtime dependency of `packages/ui`.** It is exact-pinned, so it is no less frozen than an inlined blob, but it keeps `pnpm --filter @repo/ui exec shadcn add <x>` working against the same `shadcn/tailwind.css` the vendored primitives assume, and it upgrades in one move. Ejecting would create a silent-drift failure class: CLI-added components styled against a newer contract than the vendored ones.
- **`components.json` lives in `packages/ui` only.** No app-side copy until a second app exists, so the documented extension recipe runs the CLI in that package (`pnpm --filter @repo/ui exec shadcn add <x>`).
- **The `@source` globs in `globals.css` are load-bearing and untestable by `build`.** Tailwind's class detection is rooted at the working directory, and astro runs from `apps/web`; a wrong glob drops every `packages/ui` utility with no error. `scripts/verify-css.mjs` in the tool repo asserts a `packages/ui`-only sentinel reaches the built CSS, and runs inside `pnpm deps:verify`.
- **Blocks are per-file subpath exports with no barrel.** `@repo/ui`'s root export stays project-wide constants only; a block is reachable solely at `@repo/ui/blocks/<name>`, so importing one never drags in another's dependencies. Each block is self-contained in one `.tsx` because Astro gives every `client:*` component its own React root — a compound primitive split across the `.astro` boundary would break its context at runtime.
- **The base's JS budget is now a maintained property, not an accident.** Blocks render statically unless they need browser state; only the navbar, pricing toggle and FAQ carry a client directive on the landing page. A blanket `client:load` would quietly undo the reason a static-first framework was chosen.
