# 0025 — The linter runs on the compiler we ship

Type-aware linting is done by **oxlint + `oxlint-tsgolint`**, not by typescript-eslint. This repo and the base template pin `typescript@7.0.2` in seven manifests, and typescript-eslint cannot load at all above TypeScript 6. `oxlint-tsgolint` is a native Go binary built on typescript-go that carries its own compiler, so the linter analyses the same TypeScript 7 semantics `tsc` compiles with. This is the record most likely to be relitigated by someone who sees "everyone uses ESLint" and does not know why we do not.

## Status
accepted — supersedes the ESLint-provider route taken by the 2026-08-08 grill of [`plan-linter-adoption-2026-08-08.md`](../plans/plan-linter-adoption-2026-08-08.md)

## Considered Options
- **Ultracite's ESLint provider (`ultracite/eslint/*`)** — rejected, and not for a version-lag reason. `@typescript-eslint/parser@8.66.0` reads `require('typescript').versionMajorMinor` at **module-load time** and throws when the major is >= 7. `ultracite/eslint/core` imports that parser unconditionally, so `eslint .` dies before linting a single file — the whole configuration, not just the type-aware criterion. The peer range is `>=4.8.4 <6.1.0` on both `latest` and `canary`; there is no v9 and no `next` tag. TypeScript 7 is the native Go port, so this is an API-surface incompatibility, not a bump waiting to happen.
- **pnpm `overrides` to pin a TypeScript 6 for the linter only** — rejected: `typescript` is a peer dependency and resolves from the root under both the `package.json` and `pnpm-workspace.yaml` forms. There is no way to give the linter a different compiler than the one the repo builds with.
- **Downgrade the repo (and the shipped template) to TypeScript 6** — rejected outright. Choosing a compiler to satisfy a linter is backwards, and it would push the choice onto every generated project.
- **Keep ESLint and simply not lint types** — rejected: it still does not work. The parser throws at module load regardless of whether type-aware rules are enabled.
- **Biome** — not evaluated in depth; Ultracite ships a Biome provider, but the oxlint provider already gives type-aware coverage against TS 7 and the preset set this stack needs, and adding a third candidate did not change the answer.

## Consequences
- **There is no version guard to trip and nothing to re-check on a TypeScript bump.** `oxlint-tsgolint` never loads the `typescript` npm package — verified by running type-aware rules in a workspace where `typescript` was not installed at all. Upgrading `typescript` cannot break the linter, and upgrading the linter cannot cap the compiler.
- **The dependency set is three packages, not ~35.** `ultracite`, `oxlint`, `oxlint-tsgolint`. Ultracite's oxlint presets are self-contained config data — there is no plugin-per-rule-family sprawl to hand-install, and no standing re-check burden on every Ultracite bump.
- **`oxlint-tsgolint` must be a real project dependency.** oxlint resolves it project-locally; a symlink into `node_modules` is not enough. Without it, `--type-aware` fails with *"Failed to find tsgolint executable"*.
- **oxlint discovers a `tsconfig.json` per file, and only by that literal name.** `scripts/` is configured by `tsconfig.scripts.json` at the repo root, which the discovery walk cannot see — every `node:` builtin then degrades to an error type and the `typescript/no-unsafe-*` family reports ~180 phantom violations. `scripts/tsconfig.json` is a one-line `extends` shim that makes the directory discoverable; `tsconfig.scripts.json` remains the single source of compiler options and is still what `pnpm typecheck:scripts` runs. The `--tsconfig` flag does **not** solve this — it governs import resolution, not the type-aware program.
- **`.astro` is parsed natively, with no parser wiring.** Violations are reported in both the `---` frontmatter and client `<script>` blocks. No `astro-eslint-parser`, no `languageOptions.parser` override, no plugin peer chain. Note that `ultracite/oxlint/astro` contributes an empty `rules` object in 7.10.x — it is composed for forward-compatibility, and the coverage comes from the parser.
- **The ESLint plan's `.tsx` re-application worry does not arise.** `unicorn/no-new-array` and `no-console` both fire inside `.tsx`, and type-aware rules apply there too. The `core` rule-module re-application block, and the upstream bug it was going to be filed against, are both dropped.
- **The escape route, if this ever needs reversing.** typescript-eslint gaining TypeScript 7 support would make the ESLint provider viable again, but it would cost the three-package dependency set and reintroduce the parser-version coupling this record exists to avoid. Reversing needs a new decision and a new record, not a quiet swap.
- **Ultracite is pinned at `7.10.1`, not `7.10.2`.** 7.10.2 was published inside this repo's `minimumReleaseAge: 4320` (3-day) window and cannot be installed until it matures; the two versions ship an identical oxlint preset list. Adding a `minimumReleaseAgeExclude` entry to bypass the cooldown was explicitly rejected — the cooldown is the supply-chain posture, not an inconvenience.
