# 0059 — The base merges against its release tag and keeps a deleted file deleted

[ADR 0032](0032-adr-the-base-carries-provenance-and-updates-through-the-module-path-2026-09-06.md) gave the base a record and an update path, and left every base merge two-way: the old template lived inside the old CLI, and the record said a true base would come from an on-disk copy, "never a network fetch". PrimeShopr took its base from CLI 0.5.0 to 0.8.0 and got 43 two-way base merges; for `payments.tsx` the agent rebuilt a base by hand. The same run kept putting back five demo blocks the 0.6.1 update had dropped, because their `managed` entries stayed in the manifest and the classifier read a tracked file missing from disk as `restore`. No command let the owner keep a file deleted. Settled while grilling issue [#312](https://github.com/mimukit/saasaloy/issues/312); plan: [`0103-plan-update-skipped-releases-2026-11-04.md`](../plans/0103-plan-update-skipped-releases-2026-11-04.md).

**The merge base of a base update is the template at the recorded release, fetched from its git tag.** `fetchBaseSnapshot(version)` in `packages/cli/src/lib/base.ts` downloads `packages/cli/templates/base` from `mimukit/saasaloy` at the tag `v<version>` through giget, with the module fetch's auth (`GITHUB_TOKEN` or `GIGET_AUTH`) and 60-second deadline. `update` renders it with the project's vars, as it renders the new template, and passes it to the classifier as the base revision, so a file the template did not change between the two releases is a `skip` and a changed one renders base to theirs and base to mine. **A tracked file the owner deleted stays deleted once the owner says so.** The first time `update` finds one, it sends it to the merge plan as "deleted locally"; `update --resolved <path>` then writes `deleted: true` on its `managed` entry, and no later run writes that file again.

## Status

accepted — amends [ADR 0032](0032-adr-the-base-carries-provenance-and-updates-through-the-module-path-2026-09-06.md)'s "never a network fetch" and its two-way merge plan for drift, and replaces decision 6 of the update plan ("tracked but missing, put it back")

## Considered Options

- **Snapshot the rendered base under `.saasaloy/` at `init` and `update`.** ADR 0032 named this path. Rejected as the source, kept as a later offline cache. It helps only projects made after it ships, and the case that needs it is a 0.5.0 project.
- **Fingerprint the project against every historical template.** Rejected again, as in ADR 0032. The lock names the version, so nothing needs a guess.
- **Read the template from the npm tarball of the old CLI.** Rejected. It is a larger download than the one folder at the tag, and the tag is where the source of a release already lives. The v0.5.0 tag's template hashes to the `templateHash` PrimeShopr recorded from npm (`15e9e281…`), so the two sources agree.
- **Fail the run when the snapshot is unreachable.** Rejected. The two-way path still produces a plan an agent can act on. Offline, a 404, a timeout, a `0.0.0` dev build or a version that is not a release all take that path, with the reason on the base section header, and the exit code is the one the plan earns.
- **Record the tombstone in the lock.** Rejected. The lock holds no file entries, and [ADR 0012](0012-adr-remote-first-registry-repo-is-the-registry-2026-07-23.md) keeps it the record of what resolved. A deletion is a fact about a file, so it goes on that file's `managed` entry.
- **Delete the `managed` entry.** Rejected. The next run would read the template file as new and create it again, which is the bug.

## Consequences

- **The snapshot version is chosen in one place.** `baseSnapshotVersion` takes `--from <version>` when given, else `adoptedAt` on the first update after adoption, else `lock.base.templateVersion`, else `lock.base.cliVersion`. A run that leaves a base merge waiting moves the record's `cliVersion` label and keeps its hash ([ADR 0058](0058-adr-update-notes-ship-beside-their-code-and-ride-the-merge-plan-2026-10-30.md)), so that run also writes the optional `templateVersion`: the release the hash came from. The re-run, `--resolved` included, then fetches the same snapshot and stays three-way. A clean base update writes a fresh record without the field. Unless `--from` named it, the snapshot must still hash to the lock's `templateHash`; a mismatch takes the two-way path instead of skipping the waiting merges. `--from` skips the check, because an adopted project's real start never matches the template it was adopted at.
- **The source is always `mimukit/saasaloy`.** `SAASALOY_REGISTRY_DIR` points at a `modules/` checkout and the template is not under it, so the override does not move the snapshot. `SAASALOY_BASE_SNAPSHOT_DIR` does: it names a folder of `<version>/` template copies, read in place of the tag, and a version with no folder there has no snapshot. Tests use it and never reach the network. The download honours `GIGET_GITHUB_URL` like the module fetch.
- **One tarball request per base update.** The fetch runs only when the base is outdated, once per run. `GITHUB_TOKEN` lifts the anonymous rate limit as it does for modules.
- **The new template's declaration rules both sides.** Seed files and `ownedFiles` come from the running CLI's `_saasaloy-base.json`. The old template's `_saasaloy-base.json` never enters the snapshot's file list, and a seed file is left out of both sides. An owned file the template did not change is a `skip`.
- **The old template renders with today's renderer.** The same `renderTemplate`, the project's name and testing mode, and `{{CLI_VERSION}}` set to the snapshot's own release, so the base side holds the bytes that release's `init` wrote. A render that fails takes the two-way path with the reason.
- **The tombstone is one optional field.** `managed[target].deleted: true` in `.saasaloy/manifest.json`; the entry keeps `module`, `from` and the last hash. `update --restore <path>` writes the current file and drops the flag. A tombstoned file never returns to the merge plan, `remove <module>` drops that module's tombstones, `missingBaseTargets` skips them so `outdated` reads the base as current, and `doctor` lists them as "deleted, kept deleted". An older CLI refuses a manifest with the field, because the entry schema rejects unknown keys; the downgrade refusal in ADR 0032 already stops an older CLI on a newer base record, and the field ships in the same release.
- **The classifier checks a missing file first.** A tracked file that is gone and has no tombstone is `deleted` even when the module did not change it, so the owner settles it once. A tombstoned file is `skip` while upstream left it alone and `kept-deleted` once upstream changed it, which prints `kept deleted  <path>  (upstream changed it)` in the summary and writes nothing. With no merge base, the entry's last hash stands in: a new file whose hash differs from it counts as changed. When upstream drops the file, the entry goes.
- **`--resolved` on a missing file writes the tombstone.** That covers the `deleted` verdict and a merge that ended by deleting the file alike, which `--resolved` used to untrack, so the next run created it again. The module's lock moves under the usual rule, once nothing else waits.
- **`--restore` takes only a tombstone.** A path with no tombstone, or one the run does not read (`update base --restore` on a module's file), exits 2 before anything is written. A file still waiting as `deleted` needs `--resolved` first. A tombstone `--restore` names plans its module even when the lock is current: the base counts it as missing, and a module is planned at its recorded SHA, so the restore is the one write and the lock stays.
- **A tombstoned file found back on disk was restored by hand.** It classifies like any tracked file, and the run that plans its module drops the flag. `doctor` and `--restore` no longer count it as kept deleted.
- **Adoption records only the files on disk.** `adoptBase` used to record a missing template file at its rendered hash, which the tombstone rules would now read as deleted on purpose. A missing file is listed and left unrecorded, so a later base update reads it as new and creates it.
