# 0030 — Module UI ships as a ui-package block the owner places

The base landing page discovered module UI by scanning a folder: `apps/web/src/pages/index.astro` ran `import.meta.glob("../sections/*.astro", { eager: true })` and rendered every hit in sorted filename order. A module put itself on the landing page by dropping `sections/<name>.astro`, and `waitlist` was the only module that ever used it. The convention costs nothing to author and gives the owner nothing to decide with: a module chose that it belonged on the landing page, chose nothing about where, and the page's composition came out as an accident of which modules were installed and how their files happened to sort. It also split the UI story in two, with base UI a `.tsx` block in `packages/ui/src/blocks/` and module UI an `.astro` file in the web app, along a line no user could predict.

**Module UI therefore ships as a block in the ui package, and the owner places it.** A UI-bearing module targets `@ui/blocks/<name>.tsx` and follows the rules every base block follows: one file, one component export, copy as in-file prop defaults, reached at its own `@repo/ui/blocks/<name>` subpath. `saasaloy add` writes the file and stops. It prints a pointer to the module's skill, whose required **Wire-up** section carries the import line, the tag with its client directive, and a suggested anchor on the page. Settled while grilling issue [#62](https://github.com/mimukit/saasaloy/issues/62).

**A block stays presentational, and the app injects the behaviour.** A block that has to send something takes a function prop and calls it; it imports React and ui primitives, and never an api package, an http client, or `import.meta.env`. The module ships the counterpart as a second file, a small React island under `@web/components/<Name>.tsx` that builds the client and passes the function down. This half of the record was settled during implementation, against an earlier decision to merge the whole form into one block. Two facts forced it. `packages/ui` has a `typecheck` script and the workspace is consumed as source, so a single `import type { AppType } from "@repo/api/client"` inside a block makes `tsc` compile the entire api and db source tree under the ui package's tsconfig and inherit every error in it — measured, not predicted: it turned `@repo/ui:typecheck` red with four errors. And Astro serializes island props, so a function cannot cross from `.astro` into an island; the page renders the app-side file either way.

The trade is deliberate. Install stops being fully automatic for a UI-bearing module. In exchange, page composition becomes an explicit, ordered decision the owner makes, which is the same "you own the code" stance the base blocks already take.

## Status
accepted — amends [ADR 0005](adr-0005-two-tier-convention-based-modules-2026-07-22.md), which names `apps/web`'s sections glob among its convention-based extension points. That example is now false, in the same way [ADR 0028](adr-0028-routes-register-by-chained-route-patch-2026-08-28.md) made the `routes/` glob false. ADR 0005's rule stands otherwise: no module AST-patches another module's internals, and the schema barrel still auto-re-exports `schema/`. No migration path — a project scaffolded under the old convention keeps its glob and keeps working ([ADR 0022](adr-0022-design-layer-ships-in-the-base-2026-08-06.md): base files are a one-time gift).

## Considered Options
- **Keep the glob and let a module declare its order.** A `weight` or `after` field would fix filename-sort placement without giving up the automatic install. Rejected: it settles *ordering* and leaves *placement* still decided by the module. The owner would inherit a page composed by an algorithm nobody wrote down.
- **A structured `wireUp` field on the descriptor.** The applier could print exact steps from the descriptor with no skill involved. Rejected: it reverses the settled no-`nextSteps` stance in `add.ts` — the skill is the single source of a module's procedure, and a second copy in the descriptor drifts from it. It would also duplicate what a skill has to say anyway.
- **The applier inserts the import itself.** Rejected: auto-placement is the thing this record removes. An applier that picks the position has only reinvented the glob with a worse failure mode, because now it edits a file the owner owns.
- **A wrapper block with a slot.** `<WaitlistSection><WaitlistForm /></WaitlistSection>` keeps the panel and the island separable. Rejected: two imports for one wire-up, and the wrapper renders nothing on its own. The `onSubmit` prop reaches the same separation with one import, because the app-side island renders the block rather than being slotted into it.
- **Merge the whole form into the block, api client included.** The first shape this record took. Rejected on measurement: it made `packages/ui` compile the Worker source tree on every typecheck. Keeping the block free of the api is what the `onSubmit` prop buys.
- **Give `packages/ui` the backend types instead.** Patch `@cloudflare/workers-types` and `vite/client` into the ui package so the pulled-in graph compiles. Rejected: the design package would depend on Cloudflare Worker types, the dependency would be driver-specific (needed under `database-d1`, not under `database-postgres`), and every future UI-bearing module would inherit the coupling.
- **Ship an `.astro` block into `packages/ui`.** Rejected: the package's `./blocks/*` export maps to `./src/blocks/*.tsx`, so an `.astro` file there changes the package's export contract for one module's convenience.

## Consequences
- **The descriptor gains no field.** The signal is the `files[]` target prefix, `@ui/blocks/`, resolved through the project's own `@ui` alias (`packages/cli/src/lib/ui-blocks.ts`). `add` prints the pointer when such a file lands, and **warns when one arrives from a module that ships no skill** — the convention cannot ship instruction-less, because the skill is the only place the steps exist.
- **A UI-bearing module's skill must carry a `## Wire-up` section.** The `create-module` skill states the requirement and what the section must name: the file to edit, the import line, the tag with its client directive, and an exact anchor marked as a suggestion. The skill is symlinked into the project, so the steps outlive the terminal scrollback.
- **`remove` deletes the block and cannot undo the import.** Nothing recorded which page the owner edited, so the command deletes the file it wrote and says plainly that the import line is the owner's to take out. The two `package-json-dependency` patches keep the behaviour [#36](https://github.com/mimukit/saasaloy/issues/36) describes: they are dropped with a warning, against `apps/web/package.json`.
- **`waitlist` splits along the new line.** The section wrapper and the form's markup merge into `packages/ui/src/blocks/waitlist.tsx`, exporting `Waitlist` with a required `onSubmit`; the typed `hc<AppType>` client stays in `apps/web/src/components/WaitlistForm.tsx`, which the page renders as `<WaitlistForm client:load />`. The `hono` and `@repo/api` patches and the `ImportMetaEnv` augmentation stay pointed at `apps/web`, unchanged from before. The whole block hydrates, because a static React parent cannot hold a hydrated React child.
- **A module's block copy stays in the block file.** `packages/ui/src/content/landing.ts` is a base file, and a module never edits a file it does not own, so the block carries its words as prop defaults instead. The content module's translation rules therefore cover the base blocks only.
- **A generated project's `pnpm typecheck` is unaffected.** `@repo/ui:typecheck` stays green, which is the reason the split exists. `@repo/api:typecheck` is red for an unrelated pre-existing reason (`Bindings` is not assignable to `LoggerEnv`), on this branch and on main alike.
- **The teaching surfaces that described the glob were rewritten**: `packages/cli/templates/base/AGENTS.md` and `README.md`, `apps/web/src/pages/index.astro`'s own comments, `.agents/skills/create-module`, `CONTEXT.md`, and the `saasaloy-waitlist` skill.
