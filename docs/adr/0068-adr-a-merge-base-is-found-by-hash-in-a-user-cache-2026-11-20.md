# 0068: A merge base is found by hash, from a payload in the user cache

A three-way merge ([ADR 0066](0066-adr-one-render-and-a-three-way-merge-replace-the-add-update-and-remove-engines-2026-11-20.md)) needs the bytes the CLI wrote last time. [ADR 0059](0059-adr-the-base-merges-against-its-release-tag-and-keeps-a-deleted-file-deleted-2026-11-04.md) took the base template at the recorded release from its git tag into a snapshot, chose the snapshot version from `--from`, `adoptedAt`, `templateVersion` or `cliVersion`, and checked it against one `templateHash` for the whole template. A module merged against its recorded SHA by a separate path. The manifest hash was the hash of the bytes on disk, and the flags `adopted` and `mergedWith` said when it was not the hash of a CLI write. Settled in the grill of plan [0116](../plans/0116-plan-render-and-merge-engine-2026-11-20.md), questions Q2, Q12, Q17, Q20, Q29 and Q31 (issue [#365](https://github.com/mimukit/saasaloy/issues/365)).

**The manifest hash is always the sha256 of the raw render, before Prettier, never the bytes on disk.** Each version 2 record also carries `version`, the release that wrote that render. **The base of a merge is the render of the old lock, from the payload at the old ref, and the engine accepts it only when its sha256 equals the manifest hash.** When it does not, the engine renders the project at the record's own `version`, so each record finds its own base. A `once` file written three releases ago merges against that release. A record whose source a driver gates off (`auth.sqlite.ts` in a Postgres set, through `onlyWith`) finds its base in a side rendered with that driver. When no render matches, the merge writes two-way markers, as git writes for "both added". **The payload lives in a cache for each user**, not in the project: `$XDG_CACHE_HOME/saasaloy/payload/<source>@<ref>/`, else `~/.cache/saasaloy/payload/<source>@<ref>/`. `SAASALOY_CACHE_DIR` replaces the `saasaloy/payload` part for tests. A fetch fills an entry with the whole registry at the ref and writes a `.complete` marker last. A run that needs a merge, with a cold cache and no network, refuses with exit 2. The base template at the running CLI's own release is the one bundled in the CLI, so `init` and a run that merges nothing need no network.

## Status

accepted. Supersedes the snapshot rule of [ADR 0059](0059-adr-the-base-merges-against-its-release-tag-and-keeps-a-deleted-file-deleted-2026-11-04.md): `fetchBaseSnapshot`, the version choice and the `templateHash` check give way to a render by hash, and `--from` is gone. Keeps ADR 0059's rule that a tracked file the owner deleted stays deleted, with `update --restore <path>` as the way back.

## Considered Options

- **Keep a copy of the base render inside the project.** Rejected. It adds about 300 files to the tree and doubles the diff of each update (grill Q2).
- **Hash the bytes on disk.** Rejected. A Prettier upgrade, or the owner's own Prettier config, would change the hash and break the base check. The raw render is the same on every machine.
- **Trust the old lock's render without a hash check.** Rejected. The old engine wrote files in many ways, so a render of the lock can differ from what it wrote. A base that is not the true base turns an owner edit into a silent revert.
- **Fall back to a two-way merge when the cache is cold and the network is down.** Rejected for a run that needs a merge. Two-way markers on every edited file cost more than one retry with a network. A run that merges nothing still works offline.

## Consequences

- **The flags `adopted`, `mergedWith` and `deleted` go.** The hash means one thing, so no flag has to qualify it. A tracked file the owner deleted keeps its record and stays deleted. The report lists it under "Left deleted" when upstream changed it, and `update --restore <path>` writes the current upstream file. A `generated` file is the exception: the run writes it again.
- **A version 1 project converts on its first `update`, and only there.** `add` and `remove` refuse it with exit 2 and name `saasaloy update`. The conversion finds each file's base by its recorded hash. It searches the lock's release, then every old-engine release from 0.1.0 to 0.9.0 at or below the running CLI, newest first, then each commit SHA the lock's modules resolved to. When several matching renders differ, the render nearest the disk wins. A file with no match loses its record and becomes a file on both sides. The conversion and the update are one run on a clean tree, so the result is one reviewable diff, and `--abort` restores the version 1 manifest and lock. On PrimeShopr the conversion found a base for 316 of 317 tracked files.
- **A version 1 manifest with no `hash` or no `from` refuses.** The message names `pnpm dlx saasaloy@0.9.0 update`, the last old-engine CLI, which records both. The new engine ships as 0.10.0. If it ships under another version, `LAST_OLD_ENGINE_CLI` and `OLD_ENGINE_RELEASES` in `engine/convert.ts` change with it.
- **`{{CLI_VERSION}}` renders as each side's release.** A `once` file that holds the token, such as `apps/web/DESIGN.md`, reads as changed upstream at each release.
- **The cache can grow.** Each ref the user's projects touch adds one entry. Nothing prunes it, and deleting the folder is always safe: the next run fetches again.
