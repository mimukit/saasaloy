# 0031 — Re-running `add` is the recovery for a partial apply

`saasaloy add` writes files, patches config, and links skills without a transaction. A write can fail halfway, and a file can change on disk between the moment the user approves the plan and the moment the applier writes it. The tool has never rolled any of that back, and it is not going to: `remove` is the only undo, patch reversal is [#36](https://github.com/mimukit/saasaloy/issues/36), and a rollback engine would have to un-write files the user may have already edited. **A partial apply is therefore a supported end state, and the recovery is running the same `saasaloy add <module>` again.** What this record fixes is the half that was not true: the bookkeeping used to describe the plan rather than the disk, so a run that half-applied a module still recorded it as installed, and the next `add` skipped it as done. Settled while grilling issue [#49](https://github.com/mimukit/saasaloy/issues/49).

**The invariant is that bookkeeping describes disk, for module state as much as for files.** [ADR 0006](adr-0006-copy-in-updates-manifest-hash-tracking-2026-07-22.md) already held the manifest to it, one file at a time: a managed entry means those bytes are on disk under that hash. `saasaloy.json`'s `installed` list is the same claim at module scope, and it now has to earn it the same way. `executePlan` returns `completed`, the planned modules whose file writes all landed, and `config.installed` and the lock's freshly-installed entries both derive from that list instead of from `plan.install` (`packages/cli/src/lib/applier.ts`). A run that throws mid-apply reports nothing complete, so it records no install, and the module is planned again on the next run.

**The completeness gate is authorization, not bytes.** A file held back at plan time was shown as held *before* the user approved, so the approval covers it and the module installs. A file that drifted after the approval, which the applier records as `lateDrift`, is different. The plan the user said yes to no longer describes what is on that path, so the approval does not extend to it, and the module stays uninstalled until a fresh plan shows the drift and the user approves again. That is why the gate reads only `lateDrift` and ignores `heldBack`. Patch conflicts and patch refusals never block completeness either; they are reported on their own line and file writes alone decide the install.

## Status

accepted — extends [ADR 0006](adr-0006-copy-in-updates-manifest-hash-tracking-2026-07-22.md) from managed files to module state. It supersedes nothing. The `remove` and `update` engines read the same three state files and are unaffected, because the change makes those files more accurate rather than differently shaped.

## Considered Options

- **True atomicity: stage the whole apply, then commit it.** Write every file to a temporary tree, and move it into place only when the last one succeeds. Rejected on scope and on honesty. `add` also patches files the project owns, runs alias registration, and creates native symlinks and Windows junctions, and none of those move atomically with a file tree. A staging layer would give a real guarantee for the copy step and a false impression of one for the rest.
- **A journal and an undo pass.** Record every write, and unwind the journal when a later step fails. Rejected because the unwind is the dangerous half. It has to delete files that may already be imported, and reverse patches into files the owner edits, which is exactly the reversal problem [#36](https://github.com/mimukit/saasaloy/issues/36) is open on. The failure mode of a bad undo is worse than the failure mode of a partial apply, because the partial apply leaves the user with more of what they asked for, not less.
- **Mark the module installed anyway and let `--force` be the repair.** The behaviour before this record, with the repair path named out loud. Rejected: it makes the tool lie in `saasaloy.json` and then asks the user to know a flag to undo the lie. A module absent from `installed` is re-planned by a plain re-run, dependencies included, so no flag is needed and `--force` keeps the meaning it already had (re-apply something that *is* installed).
- **Give the lock a status field, so it can say "partial".** Rejected. The lock is a provenance record: source, ref, resolved SHA, resolved graph, per installed module ([ADR 0012](adr-0012-remote-first-registry-repo-is-the-registry-2026-07-23.md)). A status field would make it a second, competing record of install state next to `saasaloy.json`, and the two would drift. An incomplete module gets no lock entry at all, which is the same answer for the same reason.
- **Exit non-zero on an incomplete run.** Rejected. A `lateDrift` hold is not a failure: nothing broke, the user's own edit outranked the plan, and the tool did the conservative thing by keeping their bytes. Scripts and CI read the exit code as "did the command work", and it did. Only a thrown apply error exits non-zero.
- **Block completeness on patch failures too.** Rejected. A missing patch target or a refused patch leaves a wiring step for the user, and `add` names the file and the reason. Withholding the install on top of that would re-plan every file write to fix a one-line edit.

## Consequences

- **`ApplyResult` carries `completed`, and two writers read it.** `executePlan` pushes only completed names into `config.installed`, and `upsertLock` pins only completed names. A module that plans no file writes completes, because nothing it planned could fail.
- **An incomplete run exits 0 and says so.** `formatIncomplete` (`packages/cli/src/commands/add.ts`) names the modules that did not install and the command that finishes them, and the closing line reports what was installed rather than what was planned. When everything lands, the two lists are identical and the output reads as it always did.
- **A thrown apply prints the recovery instead of a bare error.** `formatRecovery` states that nothing was rolled back, that the three state files describe what landed, and names the re-run. It prints only for a failure inside the apply window, where files can be on disk; a failure before or after that window is its own story and gets no such line.
- **The state files leave `add` through one path that cannot throw.** `persistState` attempts the lock pin and each of the three saves on its own and warns per failure, so one broken step no longer takes the others with it. It skips the lock entry when the source resolved no commit SHA: `provenance()` throws in that case, it used to throw first, and an unresolvable remote cost the user the manifest save behind it and reported itself in place of the error that really stopped the run.
- **`doctor` names the state this record permits.** `checkProject` in `packages/cli/src/lib/doctor.ts` reads a project's manifest and its `installed` list and reports a module with tracked work and no install as a `partial install`, naming `saasaloy add <name>` as the re-run that completes it. One finding per module, however many files it tracks. It is the only check in that file that reads a project rather than a descriptor, and the command surface for it is still open.
- **Re-running converges.** The second run re-plans the incomplete module, skips the files already byte-identical, shows the drifted ones in its own preview, and installs on approval. A repaired project ends with the same files and the same three state files as a project built by one clean run, which is what makes "re-run" a recovery rather than advice.
- **The root `package.json` merge stays after the apply.** A mid-apply throw skips it, so a run that wrote no files leaves no dependency block advertising packages nothing installed. That ordering landed with [#98](https://github.com/mimukit/saasaloy/issues/98) and this record depends on it.
- **Ctrl-C is still out of scope.** A signal during the apply kills the process before `persistState` runs, so the manifest can lag the files on disk. The next `add` classifies an untracked written file as a conflict and holds it, which is safe but not a repair.
