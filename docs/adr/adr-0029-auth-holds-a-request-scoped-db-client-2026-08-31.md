# 0029 — `auth` holds a request-scoped database client behind a module-scope singleton

`modules/auth` builds Better Auth once, at module scope, because the `plugin-array` patch point needs a module-scope `export const auth` to insert into. Its database client cannot live there. Under `database-postgres` the client owns a real TCP socket, a Workers isolate outlives the request that opened it, and postgres.js throws `Cannot perform I/O on behalf of a different request` the moment a second request reuses the first one's connection. **The singleton stays, and the client behind it becomes request-scoped**: `drizzleAdapter` binds `authDb`, a `Proxy` that reads the current request's Drizzle client out of an `AsyncLocalStorage`, and every `auth.handler` and `auth.api.*` call runs inside `withAuthScope(c, …)`, which is what puts the client there. This holds under **both** drivers, not only Postgres. Settled while grilling issue [#99](https://github.com/mimukit/saasaloy/issues/99).

## Status
accepted. It is the contract that replaced the `dependsOn: ["database-d1"]` stopgap [ADR 0026](adr-0026-database-driver-split-2026-08-28.md)'s 2026-08-31 amendment declared; that amendment now points here.

## Considered Options
- **A per-request `createAuth(env)` factory.** The obvious shape, and it needs no scope at all. Rejected on two counts. It removes the module-scope `export const auth` that `packages/cli/src/lib/patch/ts-module.ts` inserts plugins into, so the codemod would have to patch inside a function body, and `betterAuth()` would rebuild the whole instance, plugins and adapter included, on every request.
- **Swap `database-postgres` to `drizzle-orm/neon-http`.** A stateless HTTP driver is safe at module scope, so the problem disappears rather than being managed. Rejected because it discards the postgres.js client and the `withDb` cleanup helper #98 landed, ties the driver to one vendor's endpoint, and gives up the Hyperdrive path `client.ts` already supports.
- **Bind `getDb(env)` directly on D1 and make `withAuthScope` permissive there.** D1 hands the Worker a binding stub, not a socket, so nothing forces a scope on that driver. Rejected: D1 is the default, so most development happens on it, and the permissive version lets a route that forgets the wrapper pass every local test, ship, and then throw after the Postgres switch. That is after the data migration rather than during it.
- **Keep `getSession(request)` and open a client when the scope is empty.** It would spare the signature change. Rejected because that path holds no `executionCtx`, so the socket it opens has nothing scheduled to close it and nothing keeping the isolate alive for the close. That is the leak `database-postgres/files/src/client.ts` exists to prevent.
- **Export `withAuthScope` and let each caller wrap by hand.** Rejected because forgetting it type-checks, passes on D1, and throws on Postgres, which is the exact failure this record is about.
- **Narrow issue #99 so `auth` stays D1-only.** Rejected: it makes the stopgap permanent and leaves `database-postgres` a driver no feature module can be used with.

## Consequences
- **Every entry point into Better Auth runs inside the scope, and there are exactly two.** `apps/api/src/routes/auth.ts` wraps the catch-all handler, and `getSession(c)` in `packages/auth/src/server.ts` wraps the session read. Both are shipped by this module. A project that calls `auth.api.*` anywhere else has to wrap that call itself.
- **`getSession` takes the whole request context, not a `Request`.** The wrapper needs `c.env` to open the client and `c.executionCtx` to close it, and `c.req.raw` is only where the cookie arrives. The parameter type is structural and declared beside the function, so `packages/auth` still takes no `hono` dependency. The protected-route recipe in the `saasaloy-auth` skill changed with it.
- **A read off `authDb` outside a scope throws, on both drivers, with a message naming the fix.** That is deliberate rather than defensive: it is what makes the D1 development loop tell the truth about the Postgres deployment.
- **Two property names are exempt from the throw.** `drizzleAdapter` reads `db._?.schema` in its own body while `auth.ts` is still being imported, before any request exists, so `_` answers `undefined` instead of taking the Worker down on load. `then` is exempt because any `await` probes it and an unrelated promise adoption should not surface as an auth error. Symbols are exempt for the same reason: they are runtime and tooling probes, and one firing inside a logger would mask the real error.
- **The proxy implements `get` and nothing else.** The adapter reaches `db.select`, `db.insert`, `db.update`, `db.delete`, `db.query` and `db._`, and `DrizzleAdapterConfig.transaction` defaults to `false`, so `db.transaction` is never called. Methods come back bound to the real client, because `db.select()` is called as a method and an unbound function would run with the proxy as its `this`. Turning on adapter transactions, or declaring Drizzle `relations()` over the auth tables, are the two changes that make this trap set worth revisiting.
- **`node:async_hooks` is a load-bearing dependency, supplied by a flag the descriptor already set.** `modules/auth/registry-item.json` patches `nodejs_compat` into `apps/api/wrangler.jsonc` for Better Auth's own sake. Removing that flag now breaks the scope as well.
- **The scope and the driver half are separate files on purpose.** `packages/auth/src/db-scope.ts` holds the `AsyncLocalStorage` and the proxy and imports only `node:async_hooks`, so `modules/auth/files/src/db-scope.test.ts` can run it under `node --test` with no bundler and no tsconfig. `db-provider.ts` carries the workspace imports and is the file that ships in two variants. `env.ts` follows the same rule for the same reason.
- **D1 pays one property lookup per auth call for a socket it does not have.** That is the price of the two loops failing identically.
- **This is the regression the unit test pins, and it is not the whole failure.** `db-scope.test.ts` asserts that `authDb` throws outside a scope and resolves the right client inside one, which is the contract the runtime error violates. Proving the real thing needs two requests into one live isolate, so the QA case names both assertions: a sign-in succeeds, and a second request to a protected route on the same worker succeeds. One sign-in passes on a broken build, which is how the first draft's QA step missed this.
