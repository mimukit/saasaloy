# 0062: The default registry reads the release tag of the CLI that runs

[ADR 0012](0012-adr-remote-first-registry-repo-is-the-registry-2026-07-23.md) made the repo the registry and resolved a bare `saasaloy add <module>` against the live default branch. A CLI and the modules it applied then came from two different points in time. Research 0011 found the cost: the published CLI 0.8.0 read descriptors from `main`, five of them already carried a `requires.saasaloy` floor of `>=0.9.0`, and `list --json` refused with an upgrade command that installed 0.8.0 again. Every module in PrimeShopr's lock recorded `"ref": "main"`, so each `update` moved the modules to whatever `main` held, not to the release the CLI was built for (issue [#314](https://github.com/mimukit/saasaloy/issues/314)). Settled in the grill of plan [0109](../plans/0109-plan-agent-native-build-workflow-2026-11-17.md), decisions "Registry version" and "Old locks".

**With no ref, the default registry `mimukit/saasaloy` is read at the tag `v<version>` of the CLI that runs.** `RemoteRegistrySource` resolves that tag to its commit, fetches every module of the run at that commit, and the lock records `"ref": "v<version>"` with the commit SHA as `resolved`. **`@<ref>` is the explicit choice of anything else:** `saasaloy add <module>@main`, `saasaloy list @main`, and `owner/repo@ref/<module>` as before. **A plain `saasaloy update` moves every default-registry module that is not pinned to a SHA onto the running CLI's tag**, so a lock an older CLI wrote at `main` stays valid and moves on the next update, and a project that upgrades the CLI gets the modules of that release. A third-party `owner/repo` with no ref still reads its default branch, because its tags have no relation to this CLI's version.

## Status

accepted. Amends [ADR 0012](0012-adr-remote-first-registry-repo-is-the-registry-2026-07-23.md): its "the default ref is the live default branch" consequence no longer holds for the default registry, and its lockfile, SHA and `SAASALOY_REGISTRY_DIR` decisions are unchanged.

## Considered Options

- **Keep `main` and record the release tag beside the SHA.** Rejected. The record would say which release a module should match and change nothing a user runs: `update` would still move the module to `main`, and a CLI would still read descriptors written for a newer CLI.
- **Fall back to `main` when the CLI's tag is missing.** Rejected. A development build, `0.0.0`, a version bumped ahead of its release (`main` holds `0.9.0` while the newest tag is `v0.8.0`), and a release whose tag push failed would all read `main` with nobody told, which is the drift the tag exists to stop. The CLI refuses instead, as [ADR 0046](0046-adr-the-cli-runs-unattended-by-refusing-never-by-guessing-2026-10-21.md) asks. The refusal exits 2 and names the ways out: `saasaloy add <module>@main`, `saasaloy list @main`, a released CLI through `pnpm add --global saasaloy@latest`, and `SAASALOY_REGISTRY_DIR`.
- **Keep a lock entry that names `main` on `main`.** Rejected. A lock an older CLI wrote and a lock a person wrote with `@main` look the same, and the plan says `update` moves a `main` lock to the tag. A field that tells them apart would make every older CLI refuse the lock, because its schema rejects unknown keys. `@main` is a choice for one run: `saasaloy update <module> --ref main` follows `main` for that run, and the next plain `update` moves the module back to the tag.
- **Pin a third-party registry to this CLI's tag too.** Rejected. Another repository's tags follow its own releases.
- **Bundle the modules into the npm package.** Rejected again, for the reasons ADR 0012 gives. The tag is where the source of a release already lives, and [ADR 0059](0059-adr-the-base-merges-against-its-release-tag-and-keeps-a-deleted-file-deleted-2026-11-04.md) already reads the base template from it.

## Consequences

- **A module change reaches users at the next CLI release, not at merge.** CONTRIBUTING's "a module change reaches users the moment it lands on `main`" is reversed: a PR that touches only `modules/**` now needs a release to reach a plain `add`, and a module hotfix ships as a CLI patch release. Until then it is on `main` for anyone who asks with `@main`.
- **A bad descriptor on `main` reaches only `@main` readers.** Released CLIs read their tags, so the outage that the runbook "A bad descriptor reached `main`" describes shrinks to people who opt into `main`. A bad descriptor inside a released tag needs a new patch release, because a tag is never moved.
- **The tag reaches GitHub before npm publishes.** release-it 21 runs its built-in plugins in the order npm, git, github, so npm published before the tag push and a user could install a CLI whose tag did not exist yet. `packages/cli/release-npm-last.js` registers release-it's own npm plugin as a local plugin and disables the built-in one; release-it runs a local plugin after git and github in its release step. The order is now: commit, tag, push, GitHub Release, npm publish. The bump and the npm one-time password prompt are the built-in plugin's own code. `scripts/release-order.test.ts` runs release-it in dry-run mode in a throwaway repository and fails when the push does not come before the publish. Issue #312 asked for npm first; this record decides the reverse, because a tag nobody can fetch breaks every `add`, while an unpublished version only delays one.
- **The local registry is unchanged.** `SAASALOY_REGISTRY_DIR` reads a working copy and never a tag, so the smokes, the `scaffold` job and the playground keep working on a version that has no tag yet.
- **The lock records the tag's commit.** GitHub answers `commits/<tag>` with the commit an annotated tag points at, so `resolved` is always a commit SHA. `outdated` compares a default-registry module against the running CLI's tag, the same target `update` moves to. A module that a pre-tag CLI took from a `main` commit newer than the tag moves back to the tag on the next update, through the usual three-way merge with the recorded SHA as the base.
- **A floor above the running CLI prints a command that installs a version inside the floor.** The refusal now names `pnpm add --global 'saasaloy@<range>'` instead of `saasaloy@latest`. pnpm installs the highest version inside the range or fails with "no matching version", so the command never reinstalls the refused CLI. With the tag, such a floor appears mainly when a person reads `@main`.
- **`release-preflight` checks `llms.txt` against the release.** It fails when the file names a skill, a command or a flag the release does not hold. The release is the npm package (the base skills under `packages/cli/templates/base/_agents/skills/`, and the commands and flags that `saasaloy --help` and `saasaloy <command> --help` print from the CLI the preflight builds) plus the registry at the release tag, which is the commit being tagged, so a module skill under `modules/<name>/skills/` counts. `scripts/llms-txt.ts` holds the reader.
- **A coordinate may carry a ref on a bare name.** `waitlist@main` and a bare `@main` now parse; before, a ref needed an explicit `owner/repo`. One `add` still reads one source, so `waitlist@main admin` refuses and names the two.
