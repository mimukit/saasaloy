# 0023 — Generated projects ship a lint and commit-hook toolchain

The base template ships a working linter, formatter and commit-hook stack: `oxlint.config.mjs`, `prettier.config.js`, `stylelint.config.js`, `.prettierignore`, `commitlint.config.js`, `lint-staged.config.js` and `_husky/` (copied out as `.husky/`), plus `lint` / `lint:types` / `lint:code` / `lint:css` / `lint:fix` / `format` / `format:check` / `prepare` scripts and fourteen exact-pinned devDependencies. The tool repo runs the same stack over its own source, the base template, and every module's shipped files. Settled while grilling the linter-adoption plan; see [`docs/plans/plan-linter-adoption-2026-08-08.md`](../plans/plan-linter-adoption-2026-08-08.md).

## Status
accepted — extends [ADR 0022](adr-0022-design-layer-ships-in-the-base-2026-08-06.md)'s "ships in the base" argument to non-functional tooling, and reverses [#46](https://github.com/mimukit/saasaloy/issues/46)'s "the base template is excluded from linting" criterion

## Considered Options
- **A `@repo/eslint-config` (or `@repo/oxlint-config`) workspace package, as `templates/base/AGENTS.md` already claimed** — rejected because oxlint cannot consume one. `"extends": ["@repo/oxlint-config"]` fails with *"Unsupported named config … Oxlint does not support ESLint shared configs"* and exits 1; `extends` takes file paths, and JSON only. The rationale is gone anyway: it existed to keep ~30 devDependencies out of the user's root, and the linter is three packages. The claim in `AGENTS.md` was deleted rather than made true.
- **Ship the toolchain as an opt-in module (`saasaloy add lint`)** — rejected on ADR 0022's argument. Every project wants it, so an opt-in module is a step everyone takes; and modules that drop files into a project would then have to guess whether a linter exists.
- **Leave the base unlinted because it is "shipped asset code, not repo source"** — rejected. The premise was that `{{PROJECT_NAME}}` makes template files unparseable; it does not. The token appears in five files, and in the only *code* file among them (`templates/base/packages/ui/src/index.ts`) it sits inside a string literal, which is valid TypeScript. Meanwhile the base is the code every generated project starts from — the highest-leverage place in the repo for a defect to live.
- **Adopt oxfmt along with oxlint** — rejected. Prettier carries `prettier-plugin-tailwindcss` class sorting and `prettier-plugin-astro`; Stylelint carries the at-rule allow-list `globals.css` depends on. Swapping the formatter would mean re-auditing the Markdown `proseWrap` hazard on a new tool for no gain.
- **A turbo `lint` task with a per-workspace `lint` script, matching the `clean` convention** — rejected in both repos. In the tool repo `pnpm-workspace.yaml` declares `packages/*` and `packages/cli` is the only member, so `turbo run lint` structurally cannot reach `scripts/`, `modules/` or `templates/`. Downstream the reasoning differs but the answer matches: `clean` is per-workspace because each workspace generates *different* output, and linting has no per-workspace state. The template's own `typecheck` shows the hazard — it is a turbo task, but only `packages/ui` declares a script, so `apps/web` is silently unchecked.

## Consequences
- **The config is `.mjs`, not `.oxlintrc.json`, and must be passed with `-c`.** oxlint only auto-discovers `.oxlintrc.json`, and a JSON config cannot `extends` Ultracite's `.mjs` presets. oxlint documents JS/TS configs as **experimental, requiring Node.js**; we already require Node >= 24. If a future oxlint drops the format, the fallback is a generated JSON snapshot of the composed rules — workable, but a frozen copy that drifts from Ultracite silently. That risk is owned here rather than discovered later.
- **Presets are composed by concatenating arrays, never by object spread.** `ultracite/oxlint/react` declares three `plugins` and `core` declares eight; `{ ...core, ...react }` silently drops all eight. The config still loads and still reports some violations, so it looks like it works — the exact silent-success failure this whole change exists to delete. Both `oxlint.config.mjs` files carry a `mergePresets` helper and a comment saying so, and the assertion is a planted `new Array(1)` confirming `unicorn/no-new-array` fires.
- **`pnpm lint` is four passes, and the split is by invocation.** `--type-aware` is a global CLI switch with no config key and no per-override control, so the type-aware pass is scoped by *path arguments*: `packages/cli/src scripts` here, `packages/ui/src` downstream. Pointing it at shipped assets emits `typescript(tsconfig-error)` diagnostics that no override can suppress, because `@repo/tsconfig` resolves only after scaffolding and install. `.astro` is off the type-aware pass everywhere — `apps/web/tsconfig.json` includes the build-generated `.astro/types.d.ts`, which would make `astro sync` a prerequisite of every `pnpm lint`, including on a fresh clone.
- **`--deny-warnings` is load-bearing.** Ultracite sets most rules to warn and oxlint exits 0 on warnings, so without the flag the gate is a silent success. Stylelint's equivalent is `--max-warnings 0`; Prettier's `--check` already exits non-zero.
- **The suppression list is part of the config, and each entry carries its reason.** First contact produced ~670 findings across 4,851 LOC that had never been linted. Everything oxlint could fix safely was fixed; what stays off is a named list of style-tier rules that disagree with this repo's deliberate conventions (`func-style`, `no-inline-comments`, `no-await-in-loop`, `sort-keys`, the regex family, and typescript-eslint's strict-type-checked tier). No correctness rule is in that list. Re-tightening one is a code change, not a config change.
- **Never run `oxlint --fix-suggestions` on this repo.** Measured on `packages/cli/src/lib/diff.ts`: it rewrites `a[i++]` to `a[i += 1]`, which is a different program, and all 121 tests still pass. `lint:fix` is `--fix` only, in both repos.
- **Formatting reflows the whole repo once, and Markdown is excluded.** Ultracite's Prettier sets `printWidth: 80` and `proseWrap: "never"`; the second would collapse every hand-wrapped paragraph in 87 Markdown files into one line each, so `.prettierignore` excludes `**/*.md`. Prose tooling stays a separate argument.
- **Reformatting `modules/*/files/**` changes what the applier writes, and therefore the hashes in `.saasaloy/manifest.json`.** Already-scaffolded projects will see a churnier `saasaloy update` diff. It classifies as a safe **overwrite**, not **drift**, so nothing routes to AI-merge.
- **No `allowBuilds` entry is needed.** oxlint and oxlint-tsgolint ship prebuilt per-platform binaries through `optionalDependencies`, and no package in that chain declares `preinstall`, `install` or `postinstall`, so pnpm 11's build block is never hit. #46's `allowBuilds` criterion drops for a corrected reason: not "no native binaries", but "native binaries that need no build scripts".
- **Two rule families are lost by not using ESLint: sonarjs, and `unused-imports` as a distinct plugin.** `oxc` and `typescript` cover the unused-symbol ground; sonarjs's cognitive-complexity family is a nice-to-have this repo never had. Recorded so nobody rediscovers it as a regression.
- **Template dependencies stay visible to `pnpm deps:update`.** `scripts/update-deps.ts`'s Class 1 glob already discovers `packages/cli/templates/base/**/package.json`, so the fourteen new devDependencies are tracked from the moment they land, under the same exact-pin and 3-day cooldown policy ([ADR 0016](adr-0016-in-script-cooldown-gate-for-invisible-manifests-2026-07-24.md)). `pnpm deps:verify` now runs the generated project's `pnpm lint` after its build, so a template bump that breaks linting fails the standing gate.
- **Existing projects do not get this.** Base files are a one-time gift per ADR 0022 — no manifest entries, no update path. A project scaffolded before this lands adopts the toolchain by hand.
