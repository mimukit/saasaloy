# 0066: One render and a three-way merge replace the add, update and remove engines

`add`, `update` and `remove` were three engines, and each one edited a project in place. Together with the patch folder, the merge plan and the backfill they held about 11,600 of the 24,800 lines in `packages/cli/src`, and refactor survey 0003 counted five spellings of one rule in them: may the tool overwrite this file? They could not undo their own work. 106 of the 288 descriptor patches (the two `package.json` kinds) had no inverse, so `remove` left them behind, and the four table kinds appended in install order, so a table depended on install history. `update` did not merge at all. It printed three sides of each edited file into a Markdown merge plan, an agent merged the whole file by hand, and `--resolved` recorded the result. Research 0013 replayed the PrimeShopr update to 0.8.0: the old engine left 80 files for an agent. Settled by the owner on 2026-11-19 and 2026-11-20 and in the grill of plan [0116](../plans/0116-plan-render-and-merge-engine-2026-11-20.md) (issue [#365](https://github.com/mimukit/saasaloy/issues/365)).

**One operation decides every write: `apply(oldLock, newLock)`.** `render({ payload, requested, options })` in `packages/cli/src/engine/render.ts` turns a set of requested modules into a map from path to bytes and [file class](0067-adr-a-rendered-file-is-generated-merged-or-written-once-2026-11-20.md). It reads no disk and no network. `packages/cli/src/engine/apply.ts` renders the old lock and the new lock, compares each path with the disk, and picks one action: leave, write, delete, merge or report. `init` is an apply from nothing, `add X` adds X to the `requested` list of the lock, `remove X` takes it out, `update` moves the release, and `testing <mode>` changes one render option. **A patch is a transform inside the render**, applied in memory in one fixed order (dependency order, then module name), with the insert side of each codemod in `lib/patch/`. A patch has no inverse and needs none, because a remove is a render without the module. **A file with local edits merges three ways** through `git merge-file`, and JSON files merge by key with `jsonc-parser`. A conflict does not stop the run: the run writes the markers, moves the lock and the manifest, lists the file under `pendingMerges`, and exits 3. **A run that stops halfway is undone, not re-run.** The engine copies each file through `lib/backup.ts` before it overwrites, merges or deletes it, writes `.saasaloy/journal.json` before the first write, and removes the journal after the ledger. Every later run refuses with exit 2 while the journal exists, and `--abort` on `add`, `remove` or `update` restores the files.

## Status

accepted. Supersedes the write rule of [ADR 0019](0019-adr-module-patches-applied-flat-array-2026-07-24.md) (the applier applies each patch in place to the file on disk, and a remove needs reverse-patching) and [ADR 0031](0031-adr-re-run-is-recovery-for-a-partial-add-2026-09-03.md) (a partial apply is a supported end state, and a re-run of `add` is the recovery). Keeps [ADR 0034](0034-adr-update-never-writes-a-file-it-did-not-write-2026-09-09.md) by construction. Amends [ADR 0058](0058-adr-update-notes-ship-beside-their-code-and-ride-the-merge-plan-2026-10-30.md): the notes ride the update report, because the merge plan is gone.

## Considered Options

- **Change the old engines in steps.** Rejected. `update` would render while `add` and `remove` still patched files in place, so the render of an old lock would not match the bytes on disk, and each difference would become a false conflict.
- **Keep the merge plan and let an agent merge.** Rejected. Research 0013 shows that a three-way merge alone clears 17 of the 80 files, and the agent's whole-file merge was the slow step of every update.
- **Give each patch kind an inverse.** Rejected. The two `package.json` kinds cannot know whether another module or the owner still needs a dependency or a script. A render without the module answers that question for every kind at once.
- **Stop the run at the first conflict.** Rejected. A lock that stayed behind would make the next run merge over the markers. The markers are on disk, so the run moves on and exit 3 says that work is pending.
- **Keep re-run as the recovery.** Rejected. ADR 0031 refused a journal because the undo had to reverse patches into files the owner edits. The backup holds the bytes from before the run, so `--abort` writes them back and reverses nothing.

## Consequences

- **The result depends only on the set of modules.** Two install orders give the same tree, and `add` then `remove` gives the starting tree byte for byte. `packages/cli/test/matrix/` checks both for every module.
- **[ADR 0034](0034-adr-update-never-writes-a-file-it-did-not-write-2026-09-09.md) holds by construction.** The engine writes a path only when the bytes on disk equal the bytes it recorded, or when it merges three ways. It never deletes or overwrites a file whose bytes differ from what it wrote. The one exception is a `generated` file under `--force`. An edited file that upstream or a `remove` drops stays on disk, loses its record, and gets one line in the report.
- **The old engine files are deleted.** `applier.ts`, `updater.ts`, `remover.ts`, `merge-plan.ts`, `backfill.ts`, `commands/backfill-report.ts`, the inverse and refusal tables in `patch/index.ts`, and the `SAASALOY_ENGINE` flag that selected the new engine during the build.
- **`update` prints a report, not a merge plan.** The Markdown report on stdout lists the files with conflict markers, the `once` files that upstream changed, the files left deleted, the files kept and no longer tracked, the warnings and the update notes, and ends with a line that names `pnpm check`. `--resolved`, `--from`, `--out` and `--ref` are gone, and `--merge <path>` merges one `once` file. A file is resolved when no marker line remains in it, so no flag records it.
- **`add`, `remove` and `update` refuse while a merge is pending.** The refusal exits 2 and names each file in `pendingMerges` that still holds a marker line.
- **`update` takes no module name.** One update moves every default-registry module to the tag of the CLI that runs ([ADR 0062](0062-adr-the-default-registry-reads-the-release-tag-of-the-cli-2026-11-17.md)). A staged update runs an older CLI: `pnpm dlx saasaloy@<version> update`. `add` and `remove` refuse when the lock's release differs from the running CLI, and `add <module>@<ref>` refuses on the default registry. A third-party coordinate keeps its own ref.
- **The clean-tree rule is per file for `add`, `remove` and `testing`.** `update` refuses a dirty tree as before. The other three refuse only when the run must merge or delete a file with uncommitted changes, so a write of a new file needs no clean tree. `--force` overrides both.
- **There is no backfill.** The render writes every gated entry whose `when` holds, so `testing tests-after` after `testing off` writes the test files again, and `testing off` keeps each gated file on disk and drops its record. [ADR 0053](0053-adr-one-testing-mode-in-saasaloy-json-and-a-marked-agents-md-block-2026-10-23.md)'s rule that a mode change deletes nothing still holds.
- **The manifest and the lock change shape.** Manifest version 2 records `module`, `from`, `class`, `hash` and `version` for each file, plus `pendingMerges`, `pendingNotes` and `doneNotes`. The lock gains `requested`. Both schemas reject unknown fields, so a CLI from before this change refuses a project the new CLI wrote. [ADR 0068](0068-adr-a-merge-base-is-found-by-hash-in-a-user-cache-2026-11-20.md) covers the hash and the conversion of a version 1 project.
- **`add --dry-run --json` prints `schemaVersion` 3.**
